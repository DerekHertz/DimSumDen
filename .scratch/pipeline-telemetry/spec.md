# Spec: Pipeline telemetry

Status: ready-for-agent
Author: product cell, 2026-09-27

## Problem

The organism runs on a Pro plan, and we can't see where its usage goes or which errors keep coming back across cells. Cells repeat the same Grep queries, read large files, and hit the same environment failures, but nobody can see those patterns across sessions.

## Goals

1. **Error clusters**: group recurring errors across cell sessions so the user and an agent can diagnose them together and propose fixes.
2. **Tool statistics**: per cell type and per ticket, record which tools are used, how (argument patterns, repeated queries), and what they cost.
3. **Savings proposals**: turn hotspots into concrete cheaper options: a precomputed index, a dedicated helper script, or delegating to `scout`.

## Inspiration: Discretized Streams (Zaharia et al., SOSP 2013)

- **Micro-batches over an append-only log**: transcripts are append-only JSONL. Each run processes only the bytes added since the last checkpoint (a per-file offset).
- **Lineage and recomputation**: derived stats are a deterministic function of the raw transcripts. We store only aggregates and a checkpoint. Deleting the store and re-running rebuilds everything.
- **Incremental windowed aggregates**: keep per-interval buckets so rolling windows (last 5h, 7d, per ticket) are cheap sums.
- **One code path for batch and incremental runs**: the backfill over all history and the scheduled incremental run use the same pipeline.

## Decisions

| Topic | Decision |
|---|---|
| Data source | Claude Code transcripts under `~/.claude/projects/`, read-only. No hooks. |
| Scope | This organism only: the project dirs for the `agent_office` main checkout and its worktrees, including subagent sidechains. |
| Attribution | Infer cell type and ticket for past sessions from agent/subagent type, worktree branch, and lock files. Label anything else `unknown`. From now on, cells tag cell type and ticket in their first message (a protocol change behind a brain gate). |
| Errors | (a) tool results with `is_error` (failed Bash, Edit mismatches, permission denials, validation errors); (b) test/build failure patterns in tool output (vitest, tsc, npm); (c) the `Environment issues` sections of handoffs. |
| Clustering | Normalized signature: strip paths, numbers, hashes, and line/column positions, then group by tool + signature. Deterministic, with no model calls. |
| Cost | Tokens by type (input, cache-read, cache-write, output), charged to the tool call whose result fed that turn. Also show each call's share of plan usage: each scheduled run samples the 5-hour window `percentUsed` (via `get_usage` in the main session) and divides the change between samples in proportion to the tokens used. No dollar figures. |
| Proposals | Rules flag hotspots, for example the same Grep pattern repeated across sessions, large Reads, the most expensive tools per cell type, and verbose Bash output not delegated to scout. A skill has an agent turn the flags into proposals (index / helper script / delegate to scout). The user approves each one, and only approved proposals become tickets. |
| Cadence | Scheduled incremental run (e.g. nightly), plus manual on-demand runs. |
| Storage | Derived aggregates and a checkpoint in `.telemetry/` in the main checkout, git-ignored. Raw transcripts are never copied. |
| Privacy | Store metadata plus redacted arguments: redact secrets/tokens, paths outside the repo, and prompt text. Store error text only as its normalized signature, plus one redacted sample. |
| Dashboard | A standalone static HTML page generated by the script. Moving it into the Agent Office UI comes later, once the daemon and UI exist. |

## User stories

1. As the user, I open the dashboard and see the top error clusters (count, cells affected, first/last seen, a sample), so I know what breaks most.
2. As the user, I start a diagnosis session with an agent on one cluster, using the skill, and get a proposed fix.
3. As the user, I see tool calls and tokens per cell type and per ticket, broken down by tool, so I can see where usage goes.
4. As the user, I see repeated queries (the same Grep/Glob/Read across sessions) ranked by the tokens they cost.
5. As the user, I review the agent's savings proposals and approve or reject each one. Approved proposals go to the orchestrator as tickets.
6. As the user, I can delete `.telemetry/` and rebuild it from transcripts with the same results.

## Acceptance criteria

- [ ] The ingest script parses organism transcripts incrementally from a per-file offset checkpoint. A second run with no new bytes does no work.
- [ ] A full rebuild gives the same aggregates as the incremental runs over the same input (tested on fixture transcripts).
- [ ] Every tool call is recorded with cell type, ticket (or `unknown`), tool, argument shape/pattern, tokens by type, and error flag.
- [ ] Errors from all three sources are clustered by normalized signature. Tests show that paths, numbers, and hashes do not split clusters.
- [ ] Redaction is tested: no secrets, prompt text, or out-of-repo paths in `.telemetry/`.
- [ ] Plan-usage share is shown when usage samples exist, and marked "not sampled" otherwise.
- [ ] The dashboard HTML shows error clusters, per-cell/per-ticket tool and token tables, repeated queries, and pending proposals.
- [ ] A `telemetry` skill runs ingest, opens a cluster for joint diagnosis, and drafts savings proposals for user approval.
- [ ] A scheduled task runs ingest and usage sampling.
- [ ] `.telemetry/` is git-ignored.

## Out of scope

- Hooks and live streaming.
- Other runtimes (Codex, Gemini): their adapters come later through the runtime adapter (ADR 0004).
- Embedding/semantic clustering.
- Dollar cost estimates.
- An Agent Office UI panel (a later spec).
- Auto-filing tickets without user approval.
