# 01: Design question: board service, IPC and event queue

**Type:** design-question

**What to build:** An ADR amending ADR 0003. It records how cells stop writing board files directly and instead go through a single writer:
- The board service lives in the daemon.
- Cells reach it through a `board` CLI over local IPC: named pipes on Windows, Unix sockets elsewhere, or localhost HTTP with a token. Pick one and give the reasons.
- Operations are serialized in-process, and every change is appended to an event log (`events.jsonl`) that cells and the UI can subscribe to.

Markdown stays the storage format. External brokers (Redis, RabbitMQ) are out of scope unless the ADR shows they're needed. Settle the choice against ADR 0004 (OS- and runtime-agnostic) and ADR 0002 (relay, Pro-plan limits).

**Blocked by:** None (can start immediately)

**Status:** resolved

- [x] ADR states the transport, the CLI command set (claim, release, status, comment, list, subscribe), and the event schema
- [x] ADR states the fallback when the daemon isn't running: direct atomic file writes with the same CLI
- [x] ADR covers auth and exposure: local-only, and who may call it. `security` reviews this section.
- [x] Any new domain terms are added to `CONTEXT.md` (brain gate: ask first) — not added; proposed terms listed below for the user to approve.

- **Security bounce (2026-09-27):** Reviewed `docs/adr/0008-board-service.md` decision 6 at commit `0791eaf`. High-severity factual error requires a text fix before tickets 02/03 implement: decision 6's claim "a Windows named pipe defaults to an ACL on the creating user's SID" is wrong. `CreateNamedPipe`'s default security descriptor (used when no explicit DACL is supplied, which is what Node's `net.createServer().listen(path)` does on Windows) grants read access to `Everyone`/anonymous, not just the creator — a known gap (tracked upstream as nodejs/node#43070). As written, any local process, including a low-integrity one, can eavesdrop on pipe traffic. Required change: decision 6 must call for an explicit security descriptor/DACL restricting connect access to the creating user's SID (and deny `Everyone`), and ticket 03 must implement it explicitly rather than relying on defaults — Node's public `net` API doesn't set this for you. Also flag, without blocking: (1) pipe-name squatting — nothing in the ADR requires `FILE_FLAG_FIRST_PIPE_INSTANCE` semantics, so a rogue process that creates the pipe path first could impersonate the board service; decision 6 or 2 should state the daemon must fail fast (not silently coexist) if it isn't the first instance. (2) POSIX: "socket file mode 0600" is necessary but not sufficient — Linux does not enforce socket-file permission bits on `connect()`, only directory traversal permissions, so the ADR should also require the containing directory be mode `0700` and owned by the daemon's user. (3) NDJSON input validation isn't addressed: `feature`/ticket-id args must be validated against a strict allowlist pattern and path-joined-then-contained inside the board root before any fs call, to block traversal; line length should be capped to bound memory before parsing. (4) `subscribe` needs a stated backpressure/max-subscriber policy to avoid unbounded memory growth. (5) Fallback (decision 5): `O_EXCL` covers claim, but `release`/`comment` mutate markdown + append `events.jsonl` across independent CLI processes without a stated lock scope — should note whether these also take the file lock for their whole read-modify-write, not just claim. Full detail in handoff `.scratch/organism-infra/handoffs/01-security.md`.

- **Security bounce, round 2 (2026-09-27):** Reviewed `docs/adr/0008-board-service.md` at commit `048868b` against round-1 findings. The dropped transport findings (Windows DACL, pipe squatting, socket-dir perms, subscribe backpressure) correctly no longer apply — decision 5's one-line rebuttal per item is accurate, there is genuinely no pipe/socket surface now. The kept findings (path-traversal allowlist, full-mutation locking, bounded arg length) are folded into decision 6 precisely enough for ticket 02 to implement and test as literal regexes and a path-containment check. One kept item is not precise enough: decision 2's stale-lock criterion — "a lock older than a fixed staleness threshold (e.g. its holder's process is no longer running)" — conflates a time-based check with a liveness check without saying which governs, and the lock-file format specified elsewhere (cell-type + timestamp only, no PID) can't actually support a process-liveness check as worded. As drafted, an implementer could reasonably build pure elapsed-time expiry, which can steal a lock from a still-running, merely-slow operation — the exact hazard decision 2 exists to prevent. High: ADR must either (a) require the lock file record the holder's PID and require reclaim to verify that PID is dead via an OS-appropriate check before deleting the lock, with the delete-then-recreate itself race-free (re-verify via `O_EXCL` after removal), or (b) if staying purely time-based, state the threshold's safety rationale (must exceed any legitimate op's max duration; long operations must renew/touch the lock). Verdict: **Security bounce**. Full detail in `.scratch/organism-infra/handoffs/01-security-2.md`.
- **Revised (architect, 2026-09-27, round 2):** Decision 2 now splits a write lock (`{pid, host, createdAt}`, reclaimable only when host matches + pid dead via `process.kill(pid, 0)` + age past a few seconds, race-free via tombstone-rename then `O_EXCL` retry) from the claim lock (ticket ownership, never auto-expires, cleared only by `board release` or the user), per security round 2; commit `d68da87`.
- **Security pass, decision-2 recheck (2026-09-27):** Reviewed `docs/adr/0008-board-service.md` decision 2 only, at commit `d68da87` (`git diff 048868b d68da87`). This resolves the round-2 stale-lock finding correctly: the write lock now stores `{pid, host, createdAt}` and is reclaimable only when host matches, `process.kill(pid, 0)`-equivalent reports the pid dead, AND age exceeds the floor — liveness is a hard AND condition, not a hinted alternative, so a live-but-slow operation can never be reclaimed regardless of age. Reclaim is race-free: the tombstone-rename step consumes the stale lock's source path atomically, so only one of any racing reclaimers can win it (POSIX and Windows rename semantics agree here); the loser backs off rather than proceeding. The subsequent `O_EXCL` retry correctly treats a create failure as "someone else already holds a fresh lock," not fatal. PID-reuse only biases toward the safe failure mode (a reused pid reads as falsely alive, at worst delaying reclaim of a truly dead lock — never stealing a live one). Splitting the write lock (transient, per-op, reclaimable) from the claim lock (hours-long ticket ownership, never auto-expires, cleared only by `release` or the user) removes the round-1/round-2 ambiguity of one generalized "lock with a timeout." No remaining issues in this decision. Verdict: **Security pass**.
