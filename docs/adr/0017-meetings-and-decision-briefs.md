# Meetings are a bounded, ticket-scoped exception to the relay: a few cells give one take each, a chair writes a decision brief, the user decides

**Status:** proposed (drafted 2026-10-01 from the user's request in chat; the three open questions were answered the same day: up to six participants, sequential takes by default, meetings can be rejoined; not yet accepted). It amends ADR 0002 and touches the steering channel (ADR 0016), so it crosses packages and is an architect gate. The user said they "love the meeting" and ranked it after the pipeline and the crew dashboard.

**Context.** ADR 0002 chose one active cell at a time and relay handoffs over a parallel swarm, because every active cell re-sends its whole context and agent teams cost about 7x the tokens on a Pro plan. The video that sparked DimSumden shows a different shape of collaboration: the user gives a topic, picks up to six roles, each gives a short take with a confidence label and questions for the user ("Asks you"), a chair synthesizes, and the output is a **decision brief**: a question, two or three options with a recommendation, pros and cons, task counts, which roles back each option, and "only you can answer". Each participant run showed a cost of about 22 to 26 cents and the chair's about 35 cents in the video; a six-role meeting is roughly 1.7 dollars before any "dig in" reading of code. The brief is the valuable part. Running six at once is not.

**Decision (proposed).**

1. **A meeting is a board object, not a swarm mode.** It belongs to a ticket (a design-question ticket or an open scope question). It has an id, a topic, a participant list, a depth (`quick` or `dig-in`), a chair, per-role takes, one decision brief and a final user decision. It is stored under the ticket's feature on the board, so the board stays the single source of truth (ADR 0003).
2. **Participants run in sequence by default, in parallel only when the user asks.** Each take is one short cell run (read the topic and the ticket's handoffs, answer in a fixed shape), so context stays small. The cap is six participants plus the chair (the user's decision, 2026-10-01); the setup panel defaults to fewer and shows the cost of each one added; `max_concurrent_cells` (2) and the endocrine limits still apply, and a meeting auto-pauses at 90% of the usage window like any spawn.
3. **Take shape.** Claim, evidence, confidence (`sure`, `fairly sure`, `unsure`), what it would keep, what it would change, and at most one question for the user. The `scout` cell may be used for any reading a take needs.
4. **The chair writes the decision brief.** The chair is the orchestrator by default (architect for design questions). The brief has: the question; two or three options, one marked recommended; for each option the benefit, the cost, the caveat, a task count and the roles backing it; and "Only you can answer", the user-owned questions. A brief is an artifact on the board, so it survives the UI and the meeting animation.
5. **The brief is a pass gate.** It appears under Needs you. The user's choice is recorded as a gate request; the chosen option becomes tickets through the normal board path (`to-tickets`). Nothing executes on its own, and no option is applied before the user decides.
6. **Roles may decline.** A role whose contract (see the crew-dashboard spec) says the topic is outside its job returns `noop` with a reason instead of a take. That keeps a meeting from padding itself.
7. **Cost is shown, and bounded before it starts.** The meeting setup shows an estimate (participants x typical take cost + chair) against the 5-hour window, and refuses to start if the estimate would cross the usage limit.
8. **State lives on the board, so a meeting can be rejoined.** Each meeting is a directory beside its ticket (`.scratch/<feature>/meetings/<NN>-<slug>/`) holding `meeting.md` (topic, participants, depth, status: `open`, `briefed`, `decided`, `closed`), one file per take, `brief.md`, and `thread.jsonl`, an append-only log of the user's follow-ups and the chair's answers. Rejoining starts a fresh chair run that reads those files, never a resumed conversation, the same rule as a handoff (the organism-protocol skill). A follow-up may re-ask one participant; its new take is appended, and the earlier take is kept. A `decided` meeting can be reopened, which writes a new brief version rather than overwriting. The UI lists past meetings and a "Pick up where you left off" card, as the video does.
9. **Minimum viable meeting.** Ship the decision brief first, with one chair cell reading the ticket and writing the brief alone. Then add participant takes. Then add the UI (setup panel, transcript, brief view). The den's war-room table and participants walking to it are presentation, and are a later design session; a meeting must complete with no scene at all.
10. **Not in this ADR.** Live debate between participants (they never read each other's takes during the take phase, only the chair does), voice, and any cross-organism meeting.

11. **Retention: 24 hours open, then decision and summary only.** A meeting that reaches `closed` stays fully rejoinable for 24 hours. After that the bridge-independent board tooling writes `summary.md` (the topic, the question, the chosen option and why, the open questions the user answered, the tickets it produced), keeps `brief.md` and `meeting.md`, and deletes the takes and `thread.jsonl`. Later work starts from the decision and summary. Reopening after 24 hours starts a new meeting that links to the old one's summary.
12. **A rejoin seats the core members.** The chair plus a core subset, not the full original table. Core defaults to the participants whose takes the brief cites as backing the chosen option, and the user can add or drop seats in the setup panel. Any other role's earlier take stays readable; its role is re-asked only if the user adds it.

**Consequences.**

- ADR 0002 is amended: "one active cell by default" stands; a meeting is the named exception, bounded by count, depth and an up-front cost estimate. The relay for code tickets is unchanged.
- New domain terms for `CONTEXT.md` when accepted: **Meeting**, **Take**, **Decision brief**, **Chair**. UI names to be chosen in a design session (candidate: "round table", with the lazy susan as its place on the den).
- The crew-dashboard spec's `noop` and `clarify` outcomes are a dependency for decision 6.
- `security` should review one thing before build: a take is written by a cell from ticket content, so a brief must never be treated as authorization (the same rule as a gate request).

**Resolved questions (user, 2026-10-01).** Cap of six participants. Sequential takes by default. Past meetings can be rejoined, so state is saved on the board (decision 8). A closed meeting stays rejoinable for 24 hours; after that only the decision and a summary are kept (decision 11). A rejoin seats the core members, not everyone (decision 12).

**Still open.** Whether a rejoin counts against the endocrine limits as a new meeting or as one chair run (proposed: one chair run, plus any re-asked take).
