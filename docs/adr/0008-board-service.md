# Board writes go through one daemon-owned service over local IPC; markdown stays the store (amends ADR 0003)

**Context.** ADR 0003 put the board on local markdown with lock-file claims, read and written by whichever cell holds the file tools. Two pains fall out of that as the organism grows: a cell running in a worktree can't write the main checkout's board with its file tools at all (the desktop app's worktree guard blocks it — cells currently improvise shell writes as a sanctioned exception), and lock-file claims plus multi-step edits (set `Status:`, append `## Comments`, delete `.lock`) aren't atomic as a unit, so two cells can interleave and corrupt a ticket. This ADR keeps markdown as the store but gives it a single writer: a board service inside the daemon, reached by a `board` CLI, with every mutation appended to `events.jsonl`.

**Decision.**

1. **Seam.** One module, the board service, exposes six operations — claim, release, status, comment, list, subscribe — implementing markdown parsing/editing, lock semantics, atomic writes and event sequencing behind them. The module is written once and used two ways: wrapped in an IPC listener inside the daemon, or called in-process by the `board` CLI when no daemon is running (decision 5). Neither wrapper changes its behavior; this is the one seam ticket 02 and ticket 03 both build against.

2. **Transport: named pipe (Windows) / Unix domain socket (POSIX), not loopback HTTP + token.** Node's `net`/`http` modules already collapse this into one call — `server.listen(path)` — so, per ADR 0004's precedent of hiding OS differences behind one runtime-agnostic interface, the CLI and daemon share one code path and only the path string varies by platform. A pipe or socket never binds a network interface: there is no port to scan or leave open, so exposure is local-only by construction, not by a token that itself needs file-permission protection to mean anything (see decision 6). It is also cheaper per call, which matters under ADR 0002's Pro-plan relay: no TCP handshake or HTTP framing for what's normally one short request, and cells never poll it (organism-protocol already forbids polling) — only long-lived consumers (UI, orchestrator dashboard) hold a `subscribe` stream open. Requests and responses are framed as one JSON object per line (`{op, args}` in, `{ok, result|error}` out), not full HTTP semantics, so ticket 03's tests can fake the connection as a plain Duplex stream.

3. **CLI command set**, one per board-service operation: `board claim <feature>/<NN-slug> <cell-type>`; `board release <feature>/<NN-slug> --status <status> [--reason "..."]` (folds the old "edit Status:, delete lock" pair into one atomic call); `board status <feature>/<NN-slug>`; `board comment <feature>/<NN-slug> "<text>"`; `board list [--feature X] [--status Y]`; `board subscribe [--feature X] [--since <seq>]`. Reading a ticket's body stays a plain file read — markdown is still meant to be human- and agent-legible — only mutations are required to go through `board`.

4. **`events.jsonl` schema.** One JSON object per line, appended by every mutating call: `{seq, ts, feature, ticket, cell, op, from_status?, to_status?, text?}`. `seq` is a monotonic counter the service keeps (continued from the log's last line on restart); `cell` identifies cell-type plus session/worktree id; `op` is `claim`, `release` or `comment` — a bare status change outside `release` isn't a supported operation, so the schema stays small. The log is an append-only side feed for subscribers; markdown remains the sole source of truth for ticket content.

5. **No-daemon fallback.** If the CLI can't reach the pipe/socket (not found or connection refused), it calls the same board-service module in-process and performs the identical atomic sequence (`O_EXCL` lock create, markdown edit, `events.jsonl` append) the daemon would. The daemon (ticket 03) is then only a thin IPC wrapper around the module ticket 02 must build and test on its own, in-process, against a temp `.scratch/` fixture — ticket 02 does not block on ticket 03 to be usable or testable.

6. **Auth and exposure (self-contained for security review).** The service is local-only by construction: it never opens a TCP listener, so no remote host can reach it. Callers are scoped to whoever can open the pipe/socket: a Windows named pipe defaults to an ACL on the creating user's SID; the daemon creates the Unix socket file mode `0600` in a directory it owns. No bearer token is issued — the transport itself is the access control, and a token file would need the same file-permission protection to be worth anything, so it would add a moving part without adding safety. Accepted risk: this is not a new privilege boundary. Any process that can call `board` could already edit the markdown files directly today (ADR 0003's status quo); the service's job is serializing writes and logging events, not sandboxing cells from each other or from the user's own files. This matches CLAUDE.md's stated trust model — a personal, single-user local machine, not a multi-tenant service. No secrets cross this channel; ticket content is already plaintext markdown in the repo.

**Considered options.**
- *Loopback HTTP + bearer token.* Rejected: an open TCP port plus a token file protected the same way a socket path already is, for no added capability — see decision 2 and 6.
- *External broker (Redis, RabbitMQ) for the event queue.* Rejected: out of scope per the ticket, and unjustified — the daemon is a single process serializing its own event loop already, and `events.jsonl` is durable across daemon restarts; a broker adds an operational dependency to install and run on what ADR 0002/0003 keep deliberately offline and simple, without unlocking anything the socket-plus-log pair doesn't already do.
- *Full HTTP framing over the pipe/socket*, so curl-like tools could call it. Rejected: nothing in the command set needs headers, methods or content negotiation; newline-delimited JSON is trivial to fake in tests and cheaper to parse.

**Consequences.**
- Ticket 02 (board CLI) builds and tests the board-service module entirely in-process, then adds a "probe the socket path, else call in-process" branch; it does not need a running daemon to be complete.
- Ticket 03 (daemon board service) adds only the IPC listener (`net.createServer().listen(path)`) and the line-JSON framing around ticket 02's module; its tests can drive it with a real client connection or a faked Duplex stream.
- `.lock` files stay the on-disk claim marker, format unchanged, so a lock created by today's shell-write fallback and one created by the future daemon are interchangeable. This ADR concentrates who writes the board; it does not require migrating the claim mechanism.
- No CONTEXT.md changes made here. "Board service," "IPC transport" and "events.jsonl" are architecture vocabulary, like "runtime adapter" in ADR 0004, not user-facing domain concepts — flagged for the user below in case they want otherwise.
