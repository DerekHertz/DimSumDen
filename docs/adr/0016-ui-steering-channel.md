# The UI steers live cells through the bridge: SSE down, authenticated POST up, a `CellRuntime` adapter whose Claude implementation runs headless stream-json child processes the bridge owns, with a three-slice path from "dispatch, watch, approve, kill" to full steering

**Status:** accepted (user, 2026-09-30, in chat; drafted by the architect, 2026-10-01). It touches `apps/bridge`, `scripts/` and docs, so it crosses packages (an architect gate). **Amended in place twice (architect, 2026-10-01):** (1) after the first `security` review bounced decision 6 (handoff `11-security-2.md`): dispatch consent is bound to the UI token and approval requires the full tool input; the medium and low findings are folded in or deferred with a reason (decision 6, "Security review round 1"). (2) After a user constraint (via the orchestrator, 2026-10-01): the user runs from the Claude desktop app and cannot use `claude --bg`, so the primary Claude adapter is now headless `claude -p` stream-json children, not `--bg` sessions, and nothing assumes a terminal-started bridge (decisions 2, 3, 6, 7). (3) **Amended a third time (architect, 2026-10-06)** after the `security` pre-build review of decision 6 (handoff `106-security.md`, findings F1 to F8): a one-time launch code replaces the printed token, the child's own inbound socket is a spike before the adapter, the `control_request` contract is spelled out, the argument builder is an allowlist, the child's setting sources are restricted, kill escalates, and slice 1 is built in an order that puts the auth gate before any mutating route (decisions 2, 3, 6, 7; "Security review round 2"). Route and type names here keep the 2026-09 vocabulary (cell, `/cells`, `CellHost`); ADR 0019 decision 10 renames them (agent, `/agents`, role) before anything is built, and the tickets use the new names. **Still open:** `security` re-reviews this amendment together with the S8 result before the adapter builds; the billing facts for headless runs are unconfirmed (see decision 2); and the domain terms (Steering command, Permission request) and the Gate request rewording were added to `CONTEXT.md` on this branch (orchestrator, at the user's request, 2026-09-30).

**Context.** Ticket `organism-infra/11` asks for the channel that lets the UI watch and steer live cells: an inbox for tool-permission requests, taking over or pairing, a message mid-task, kill, and sub-second live state. ADR 0008 decision 8 left it open; ADR 0004 fixed only the adapter's verbs (spawn, stream events, send message, approve/deny, stop). The user's goal (2026-09-30) is to drive agent work from the UI within a day, so this ADR also names the thinnest first slice. Facts that shape the design:

- Today the UI cannot reach a cell. Cells are subagents the orchestrator launches with its Agent tool inside an interactive desktop-app session; nothing outside that session holds a handle to them.
- The bridge (ADR 0011) already serves `GET /state`, an SSE `GET /events`, and `POST /requests`, behind a loopback bind and Host/Origin/Content-Type checks. The bridge has no Board write path, and a Gate request "never runs anything itself" (`CONTEXT.md`).
- The user decided on 2026-09-28 that the event source is transcript tailing (`~/.claude/projects/<cwd>/<session>.jsonl` plus the subagent transcripts beside it), one reader for tool-call animation and cost, with the hook design as a fallback. This ADR changes the primary source to the child's own stdout stream (same line shape, same parser); see Conflicts.
- ADR 0001: cells are unmodified `claude` CLI processes on the owner's login; no model API, no Agent SDK.
- **The user works from the Claude desktop app and cannot use `claude --bg`** (user constraint relayed by the orchestrator, 2026-10-01). The bridge therefore cannot rely on background sessions, `claude agents`, `claude attach` or `claude stop`, and cannot assume it was started from a terminal.
- The installed CLI (2.1.284, checked with `--help` for the first draft) has headless `claude -p --input-format stream-json --output-format stream-json` and `--permission-prompt-tool`, `--session-id`, `--resume`, `--settings`, `--agent`.
- Evidence gathered (a throwaway probe in the architect's scratchpad, plus a `scout` read of the official docs; not committed). Proved: the binary accepts the stream-json flags and `--permission-prompt-tool stdio`, and emits `system/init` with `session_id` in about 0.5 s. Not proved: any model-backed behaviour. A `claude` spawned from the architect's sandbox answers "Not logged in", so the permission request and response shapes, the stdin user-message shape, mid-turn messages and `--agent` under `-p` are all unverified here. From the docs: `--resume <id>` reopens a session; SIGTERM leaves a turn unfinished; the `--permission-prompt-tool` request/response shape is undocumented. The same support article (as read by `scout`, 2026-10-01) says `claude -p` usage has drawn from a separate monthly credit instead of plan usage since 2026-06-15. That is unconfirmed (see decision 2).

**Decision.**

### 1. Transport: the bridge grows in place; SSE down, POST up

The UI talks to the existing bridge process over its existing localhost HTTP surface. There is no separate daemon process and no second port. ADR 0011 said the daemon would later replace `apps/bridge` behind the same surface; this decision makes that literal: `apps/bridge` gains a `cells/` module and stays the one process the user starts. `organism-infra/03` (board IPC) stays parked under ADR 0008 decision 5; this ADR does not revive it.

- **Down (cell state to the UI):** the same SSE stream (`GET /events`). New additive snapshot keys and `change` types (decision 4). Sub-second delivery needs no polling: a cell event reaches the stream as soon as the child's stdout line is parsed.
- **Up (commands to the daemon):** `POST` JSON routes (decision 3), each one command, each answered with 200/201 or a 4xx that names the refusal.

Why not a WebSocket: the traffic is low-rate commands up and a firehose down, which SSE plus POST already model. A WebSocket handshake is not covered by CORS, so it would need its own Origin enforcement, and framing needs a dependency (`ws`) or hand-rolled code. SSE plus POST reuses ADR 0011's tested hardening (Host check, Content-Type, Origin, body caps, SSE back-pressure destroy) unchanged and adds no dependency. Why not a named pipe or Unix socket: a browser cannot open one (ADR 0008 decision 8). Why not a second "daemon" port: it would double the exposure surface for no capability.

### 2. How a steering command reaches a live cell: `CellRuntime` (refines ADR 0004)

One module interface, `apps/bridge/cells/runtime.mjs`. ADR 0004's verbs, made concrete: a runtime spawns a **cell process**, and each live cell is one such object, so the interface stays small and the host owns the handle map. A capability set lets a runtime say what it cannot do (the lowest-common-denominator rule):

```
CellRuntime = {
  id: "claude",
  capabilities: { spawn, stop, approve, send, handover },     // booleans; the UI greys out what is false
  spawn({ cellType, mode?, ref, cwd, prompt, model?, sessionId, resume? }) -> Promise<CellProcess>
}
CellProcess = {
  handle,                                            // opaque string; key in the host's map
  events: AsyncIterable<CellEvent>,                  // tool start/end, message, usage, permission-request, state, done
  stop() -> Promise<void>,
  send?(text) -> Promise<void>,
  decide?(requestId, { allow, reason? }) -> Promise<void>,   // answers a held permission request
  resumeCommand?() -> string                         // shown to the user; the bridge never runs it
}
```

The adapter builds the child's environment itself (an allowlist, decision 6.6), so it is not a parameter. `startBridge({ root, port, uiDir, runtime })` takes the runtime as a parameter, defaulting to the Claude adapter. Tests pass a fake runtime. Two adapters (Claude, fake) make this a real seam.

How the **Claude adapter** carries each command (the answer to "hooks, stdin, signals"). The bridge spawns `claude` as its own child with piped stdio and holds the pipes, so the bridge opens no inbound route for a cell. (The child itself may open one: every `system/init` carries a `messaging_socket_path` under `/tmp/cc-socks`, see 6.3 and spike S8.)

| Command | Mechanism | Slice |
|---|---|---|
| Dispatch | create a worktree, then spawn `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --session-id <uuid> --agent <cell> --setting-sources project,local --strict-mcp-config --settings '<inline deny JSON>'` (the fixed template of 6.6) with cwd in it; the prompt is the first stdin user message; the bridge mints the session id | 1 |
| Watch | parse the child's stdout stream-json lines into `CellEvent`s with `parseClaudeLine` | 1 |
| Kill | close stdin, wait a bounded grace (`KILL_GRACE_MS`, 5 s, one constant in `cells/policy.mjs`), then SIGTERM, then SIGKILL after a second grace, on the `ChildProcess` the bridge itself spawned this run (the conversation is kept and `--resume` reopens it); never a pid from a file or a request. Whether the child's own subprocesses (Bash tool grandchildren) are signalled too is decided by spike S4b (below) | 1 |
| Approve or deny a tool permission | the CLI writes a `control_request` (`request.subtype == "can_use_tool"`, decoded under 6.5) on stdout; the host holds it as an approval until the UI decides, then writes the matching `control_response` on stdin. Timeout, expiry, bridge shutdown or any request the decoder does not accept answers **deny** | 1 (only if spikes S3 and S8 pass; else slice 2) |
| Message mid-task | write a user message line on the child's stdin | 2 |
| Take over or pair | **hand over**, not pair: stop the child, then the UI shows `claude --resume <sessionId>` for the user's terminal, run in the cell's cwd. Two live processes never share a session. Live pairing is not offered | 2 |

The exact shapes of the stdin user message, the `control_request` and the `control_response` are undocumented and unverified; spikes S1 to S3 fix them before slice 1 builds. Nothing outside `cells/claude-adapter.mjs` may name a Claude flag or message shape.

**Process lifetime.** Children belong to the bridge, and the bridge ends every child it started the same way a user kill does (stdin close, grace, SIGTERM, grace, SIGKILL):
- A **shutdown handler** runs the kill sequence on every live child on `SIGINT`, `SIGTERM`, `SIGHUP` and an uncaught exception, and sends SIGKILL synchronously from the `exit` event (no await is possible there). The host sets `state: "terminated"` and writes the `sessions.jsonl` line only after it has seen the child exit, never before.
- Closing stdin ends an **idle** child (spike S1). Whether it also ends a child **in the middle of a tool call**, and whether a Bash tool's own subprocesses (a dev server, `npm test`) outlive the SIGTERM, is unproved. Spike S4b settles both. If grandchildren survive, the adapter spawns the child as a process-group leader (`detached: true`, so it is its own group, still holding the bridge's pipes) and signals the group (`process.kill(-pid)`) on the SIGTERM and SIGKILL steps. That is still a signal to a child the bridge spawned this run, so decision 6.9 holds.
- A bridge that is itself SIGKILLed or crashes cannot run any handler. The only protection then is stdin EOF (S4b). On the next start the host cannot know whether a previously live child is still running (6.9 forbids reading a pid from a file), so it marks those cells `terminated` with reason `bridge-restart-unverified`, not `bridge-restart`, and the UI shows the `claude --resume` command with a note that the old process may still be alive.

Cells do not survive a bridge restart in the normal case. This is the cost of owning the pipes; it removes the pid-reconciliation and process-verification problems of a detached design.

**Background sessions are an optional later adapter mode, not part of slices 1 to 3.** `claude --bg` plus an HTTP `PermissionRequest` hook would let cells outlive the bridge, but the user cannot use it now. If adopted, it needs its own security review, because it adds an inbound hook route and a hook token. The requirements from review round 1 carry over to it: an `Origin` exemption for the hook route with a Host check, a per-session hook token (at least 128 bits) delivered by environment only, never argv or a file, with a canary spike proving the environment allowlist holds under `--bg` (a background session may take its environment from the CLI's supervisor); a 256 KB body cap; the UI token rejected on the hook route and the hook token on every UI route; and a registry-pid kill fallback only after verifying the process command line and start time.

**Billing and ADR 0001 (open question; not asserted).** Headless `claude -p` is still the unmodified CLI on the owner's login: no SDK package, no API key, no model API, so it satisfies the letter of ADR 0001. Whether it satisfies the intent (cells run on the owner's plan usage) depends on a fact nobody here has confirmed: the support article read by `scout` says `claude -p` usage has drawn from a separate monthly credit since 2026-06-15. If that is true, daemon-spawned cells would be metered apart from the interactive session, the usage guard (which reads plan usage) would not see their consumption, and ADR 0001 and ADR 0002's auto-pause would need amending. If it is false, nothing changes. This ADR neither assumes nor rules out either answer. Spike S5 measures it (a plan-usage reading before and after one trivial headless run, plus the account's usage page), and the user confirms. Until the user does, slice 1 may be built and exercised on trivial prompts, but headless dispatch is not adopted as the default way to run relays.

Fail-closed rule for every adapter: a permission request with no decision (timeout, expiry, bridge shutdown, hostile or unparseable request) is answered deny or left unanswered by a dead child. The bridge never auto-allows.

**One line parser, one source.** Transcript lines and stream-json stdout lines share the message shape (`message.content` blocks, `message.usage`). `parseClaudeLine(line) -> CellEvent[]` is that one parser. The child's stdout feeds it directly; this keeps the user's "one reader feeds animation and cost" decision, with a pipe instead of a file. A transcript tailer (an `fs.watch` incremental read of `~/.claude/projects/<cwd>/<session>.jsonl` and its sibling subagent files) is kept as a secondary feeder, enabled only if spike S2 shows the stdout stream omits subagent activity. Pipe latency should be well under a second; unverified, S2 measures it. Permission requests arrive on the same stream and do not depend on the tailer. Cell output is untrusted text; the input rules are decision 6.8.

### 3. Routes and the `CellHost` module

Behind the routes sits one deep module, `CellHost` (`apps/bridge/cells/host.mjs`). The routes are thin; the module owns the policy, the live-cell map, the registry and the event merge.

| Route | Body | Does |
|---|---|---|
| `POST /session` | `{ code }` | redeems the one-time launch code for a session token (decision 6.2); Host, Origin, Content-Type and body cap, no Bearer |
| `POST /cells` | `{ ref, cellType, mode? }` | dispatch (below); **the only HTTP way a cell starts**; Bearer token |
| `POST /requests` | ADR 0011's Gate request body | records an audit line; runs nothing; now Bearer token and required Origin (decision 6.1) |
| `POST /cells/:id/stop` | none | kill |
| `POST /cells/:id/message` | `{ text }` (at most 2 KB) | send (slice 2) |
| `POST /approvals/:id` | `{ decision: "allow" \| "deny", note? }` | answer a permission request |
| `GET /approvals/:id` | none | the full tool input for a pending request, token required |

There is no inbound hook route: permission traffic rides the child's pipes, never the network.

**Dispatch policy** (all refusals write nothing and start nothing):
- **Consent is the token, not a file line.** A cell starts only from a Bearer-token `POST /cells`. The bridge never starts a cell because it saw a `dispatch-approve` line, whether that line arrived through `POST /requests` or was appended straight to `.scratch/_requests/requests.jsonl` by a process on the same account (any cell can do that). The Run button calls `POST /cells`; the bridge itself then appends the `dispatch-approve` line (with `outcome: "dispatched <cellId>"`, ADR 0011 decision 6's append-only form) as an **audit record, not proof**: a line in that file proves nothing about who wrote it.
- `ref` names a ticket in the snapshot with `gate == "dispatch"` (ADR 0011 decision 3).
- **Known residual (not closed here):** the orchestrator genome (step 2) still reads `requests.jsonl` and treats a `dispatch-approve` line as the user's answer, so a prompt-injected cell can forge a line and talk the orchestrator into acting. This is the same posture as before this ADR, and no UI token defends it, because the orchestrator cannot verify who wrote a line. Follow-up ticket proposed: bridge-signed request lines (the bridge appends an HMAC under a key the cells cannot read) plus an orchestrator genome change to accept only signed lines; the genome edit is the orchestrator's to make with the user's permission.
- `cellType` is one of the nine known cells. **Slice 1 dispatches only `orchestrator` and the non-relay cells (`architect`, `product`, `designer`, `scout`).** Relay-hop cells (`developer`, `qa`, `security`) are refused with 409 "dispatch the orchestrator": the orchestrator owns the hop SHA, the Jev tier and the verify depth, and re-implementing that in the bridge would fork the relay. (ADR 0019 decision 3 moves that logic into the bridge's relay runner, which starts hops through the host's internal `start()` entry, never a route. The 409 stays on the **route path**, keyed to the entry point and not to any field of the request body; `start()` is not reachable from HTTP; it shares the one synchronous reservation and the caps below. Whatever starts a relay later is itself a token-authenticated route.)
- `orchestrator` runs in the main checkout (as it does today) with a daemon-built prompt that cites the request id and says to read it with `scripts/requests.mjs --list`. Non-relay cells get a detached worktree under `.claude/worktrees/<cell>-<NN>-<shortid>` at the main `HEAD`, and a prompt whose first command is the same `node scripts/cell-start.mjs --base <sha> --branch <cell>/<NN>-<slug> --ticket <ref> --cell <cell>` line the orchestrator writes today. The prompt is a fixed template filled only with validated fields (`ref` matches `^[a-z0-9][a-z0-9-]*/\d{2}-[a-z0-9][a-z0-9-]*$`, so no segment starts with `-`; `cellType` from the allowlist); no client string reaches it. If `--agent <cell>` is not honoured under `-p` (spike S1), the template's first line tells the cell to read `.claude/agents/<cell>.md` and follow it, which `CLAUDE.md` already allows.
- Concurrency: refuse when running daemon-spawned cells would exceed `max_concurrent_cells` (2 per CLAUDE.md, ADR 0002; one constant in `cells/policy.mjs`). The check and the live-map reservation (one live cell per `ref`, the live-count slot, the 8-session cap) are **one synchronous step** with no `await` between them, so two near-simultaneous clicks cannot both pass; a test fires two `POST /cells` concurrently with one slot left. Usage: refuse at a five-hour reading of 90% or more (ADR 0002's auto-pause). A `null` reading allows the dispatch and says so in the response. (If headless runs draw from a separate credit pool, this reading does not see them; see decision 2.)
- Permissions: the argument builder is an **allowlist, not a denylist**. Production argv is one fixed template, and the only variable parts are a bridge-minted session UUID, a `--agent` value from the role allowlist, an optional `--model` from a fixed list, and the bridge's own inline `--settings` JSON. There is no `extraArgs`, no `allowedTools` option and no passthrough, so `--allowedTools`, `--add-dir`, `--mcp-config`, any `--permission-mode` and the skip-permissions flags cannot be constructed (decision 6.6 has the test). Spawned cells take their effective permissions only from the repo's own `.claude/settings.json` and `settings.local.json`, plus the bridge's inline deny rule (decision 6.10, a partial measure). A tool outside the allowlist becomes a pending approval in the UI (slice 1, if S3 and S8 pass). If either fails, the adapter omits `--permission-prompt-tool`, the CLI denies unlisted tools on its own, and the cell reports the failure.
- Board: the bridge still has zero Board write paths (ADR 0011). The spawned cell claims, comments and releases through `board`, as today.

### 4. State the UI sees (additive keys on ADR 0011's snapshot)

```json
{
  "cells": [{
    "id": "c-7f3a19d04be2c685", "ref": "organism-infra/11-daemon-ui-cell-channel-design", "cellType": "architect",
    "mode": null, "runtime": "claude", "sessionId": "08376463-453a-4135-a7df-4ee921c22e86",
    "state": "working", "startedAt": "2026-10-01T09:00:00.000Z", "lastEventAt": "2026-10-01T09:03:12.410Z",
    "tool": { "name": "Read", "summary": "docs/adr/0011-..." },
    "tokens": { "input": 41200, "output": 3100 },
    "capabilities": { "stop": true, "approve": true, "send": false, "handover": true },
    "resume": null
  }],
  "approvals": [{
    "id": "a-91d07c3e5b2a4f68", "cellId": "c-7f3a19d04be2c685", "tool": "Bash", "summary": "npm test (first 200 chars, secrets masked)",
    "inputLength": 1840, "truncated": true,
    "ts": "2026-10-01T09:03:12.410Z", "expiresAt": "2026-10-01T09:13:12.410Z", "state": "pending"
  }]
}
```

- `resume` is `null` while the child runs; once the cell is stopped, done or terminated it is `claude --resume <sessionId>` (a string for the user's terminal; the bridge never runs it).
- **`summary` is a display hint, never the basis of an allow.** It is capped at 200 characters, so a padded command can hide its tail past the cut. The snapshot therefore also carries `inputLength` and `truncated`, and the allow action is gated on the full input (decision 6.5): the UI must fetch `GET /approvals/:id` and render the whole input before `allow` is enabled; `deny` is always enabled.
- `state` is one of the director's `STATES` (ADR 0007): `working`, `waiting_on_user` (a permission is pending or the session is idle awaiting input), `blocked`, `done`, `failed`, `throttled`, `terminated` (killed by the user, or ended by a bridge restart), `idle`. `snapshotStateSource` (ADR 0011 decision 7) can key off it directly, so nothing new is animated.
- `change` types added: `cell` (full object, or `null` when it leaves), `approval` (full object). Same `seq` rules as ADR 0011 decision 5; unknown types stay ignored.
- `tool` and `tokens` come from the line parser. Cost-pricing and the telemetry reader are a separate ticket; this ADR only fixes that the same parser feeds them.
- Registry persistence: an append-only `.scratch/_run/sessions.jsonl` (spawn, decision, stop; one line each, with `ts`, `cellId`, `ref` and, for decisions, the request id and the acting route). On start the host replays it for history and marks cells that were live as `terminated` (decision 2, process lifetime). `.scratch/_run/` should be git-ignored; the developer adds that line to `.gitignore`. **The file is untrusted input** (any cell can write it, same account): replay validates every field (decision 6.9), drops lines that fail, and nothing read from it is ever signalled or executed.

### 5. Test seams

Two, at the highest points:

1. **`startBridge` over HTTP, with a fake `runtime` injected.** Dispatch validation and refusals, concurrency and usage limits, auth rejections, kill, the permission round-trip (the fake emits a permission request, `POST /approvals/:id` releases it with the right response, timeout answers deny), the SSE `cell` and `approval` events, bridge-restart marking, and the security assertions in decision 6 (token and Origin on every mutating route including `POST /requests`, table-driven from the route registry so a new route is covered by default and an unauthenticated caller never sees a 404 or 409; a forged `requests.jsonl` line or `POST /requests` starts nothing; `OPTIONS` carries no `Access-Control-Allow-*`; `allow` refused until the full input was served; the concurrent-dispatch race). The existing `bridge-*.test.mjs` fixtures extend.
2. **`claude-adapter.mjs` as pure functions over fake pipes:** the argument builder (including the "no permission-broadening flag" and "no secret in argv" assertions), `parseClaudeLine` over recorded lines plus hostile ones (malformed JSON, oversize line, no newline), the `control_request` decode and `control_response` encode (decision 6.5), and the child-process wrapper driven by a stub script that speaks the stream. Fixtures are real captured lines, committed under `apps/bridge/cells/fixtures/`. If the transcript tailer is enabled, its path builder joins this seam.

The adapter against a real `claude` is a manual conformance script (`apps/bridge/cells/conformance.mjs`), not a CI test, because it needs the owner's login, which a cell's sandbox does not have. The user (or a developer working in a session that has the login) runs it; slice 1's first task is to run it (spikes below).

### 6. Auth and exposure (`security` reviews this section)

Threat model, in order of likelihood: (a) a web page in the user's browser firing requests at localhost (CSRF, DNS rebinding); (b) **a cell itself** (an agent, possibly prompt-injected) running `curl` against the bridge, or writing files on the same account, to approve its own permission request, dispatch, or kill another cell; (c) another local OS user on a shared machine; (d) malformed or hostile cell output (stdout or transcript lines).

The principle that follows from (b): **the UI token is the only proof of user intent.** A file line, a snapshot id or an unauthenticated request proves nothing, because a cell can produce all three.

1. **Bind, Host, Origin, preflight.** Loopback `127.0.0.1` only, not configurable (ADR 0011). Every route keeps the Host check. Every mutating route (`POST /cells`, `POST /cells/:id/stop`, `POST /cells/:id/message`, `POST /approvals/:id`, **and `POST /requests`**) additionally **requires** an `Origin` header equal to `http://127.0.0.1:<port>` or `http://localhost:<port>` (a browser always sends one on a cross-site POST; ADR 0011 only checked it when present), `Content-Type: application/json`, a valid Bearer token (item 2), and the 4 KB body cap. `GET /approvals/:id` needs the token too. Failures return 403 or 401 and write nothing. There is no exemption and no hook route: permission traffic never crosses the network (item 3). `OPTIONS` on any mutating route returns no `Access-Control-Allow-*` header. If the Vite dev origin is ever allowed, it is one exact allowlist entry, never a pattern. Tests assert each of these. *(Round 2, F7:)*
   - **One route registry, default deny.** Every route is a row in one table (`cells/routes.mjs` or the bridge's equivalent): method, path pattern, `auth` (`none` for the unauthenticated reads, `origin` for `POST /session`, `token` for the rest) and `mutating`. The router serves only registered rows; anything else is 404 with no side effect. The auth tests are table-driven from that registry and enumerate it, so a route that is added or renamed (ADR 0019 decision 10: `/cells` becomes `/agents`) is covered by default, and a mutating row missing from the auth tests fails the suite.
   - **Auth runs first.** Host, Origin, Content-Type, body cap and Bearer are all checked before any route parameter, ticket ref, cell id or approval id is looked up, so an unauthenticated caller gets 403 or 401 and never a 404 or 409 that confirms a ticket, cell or approval exists. A test sends each mutating route with a real and a bogus id and no token and asserts identical responses.
   - **Nothing disables or presets the token.** No environment variable, CLI flag, config file or request field turns the check off or supplies the token or launch code. Tests inject them only through a `startBridge` option (`auth: { launchCode, ttlMs, now }`); the production entry point passes none.
2. **One-time launch code, then a per-run session token** *(round 2, F2: the fragment URL lands in the browser's history database and, if an agent's tool call ever starts the bridge, in a transcript under `~/.claude/projects`, both readable by any cell on the account; so the printed secret must be worthless once used)*. At start the bridge generates a **launch code** (32 random bytes) and prints one launch URL with the code in the fragment: `http://127.0.0.1:4317/#code=<...>`. The code is **one-time and short-lived**: it expires after `LAUNCH_CODE_TTL_MS` (5 minutes, one constant) and is burned on its first successful redemption; five failed redemptions also burn it. The UI reads the fragment, removes it from the address bar, and sends `POST /session` with `{ code }` (Host, Origin, Content-Type and body-cap checks; no Bearer, since none exists yet). The bridge answers with a **session token** (32 random bytes, in the response body only) and keeps up to four live session tokens **in memory only** (not on disk, not in the environment of anything it spawns); all die with the bridge. The UI keeps the token in memory and sends `Authorization: Bearer <token>` on every route in item 1. A leftover URL in history or a transcript is therefore inert: the code is spent or expired. A reload loses the in-memory token and needs a fresh launch code; how the user gets a new one without restarting the bridge is part of "How the bridge is started" (decision 7), which is still open. The token is accepted **only** in the `Authorization` header, never a query string, and never appears in a log line, an error body or the snapshot; the code is likewise never logged. The printed URL goes to the bridge's own console only: never in argv (for example to `open <url>`, which `ps` shows), never written to a log or file. **The user starts the bridge, never an agent's tool call** (decision 7), because a code printed into a cell's transcript is readable by any cell until it is spent or expires; the window is five minutes and ends at the user's first click. A custom header also forces a CORS preflight the bridge never answers, which stops cross-origin scripts even if the Origin check had a hole. The comparison hashes both sides with sha256 and uses `crypto.timingSafeEqual` on the digests (the raw call throws on unequal lengths); any failure, including a malformed header, returns 401, never 500. Why not write the token or code to a file: a cell runs as the same OS user and can read any 0600 file the user can, which defeats threat (b). A cell also cannot find it in the bridge's environment because there is none. **Residual, stated plainly:** a cell that reads the launch code from a transcript or the history database in the window before the user's click can redeem it first and hold a session token. The window is bounded and the user's own click then fails visibly ("code already used"), which is the signal to restart the bridge. **Scope, said plainly:** the token gates the bridge, not the operating system. A process on the same account can still signal another process it can see; this ADR does not close that.
3. **The bridge opens no inbound permission route; the channel is the child's pipes, but the child's own socket is unverified (F1).** The bridge adds no hook route and no hook token, and a cell cannot submit a permission request or a decision through any route of the bridge. A cell can only write to its own stdout, which the bridge treats as untrusted text (item 8). A permission request gets a bridge-minted approval id bound to that child. **The claim "no other process can answer it" is withdrawn until spike S8 passes.** Every `system/init` in the S1 and S3 fixtures carries `messaging_socket_path: /tmp/cc-socks/<pid>.sock` and `capabilities` including `interrupt_send_now_v1` and `msg_lifecycle_v1`: the child itself listens on a pid-named Unix socket. If that socket accepts user messages, interrupts or a `control_response` from any local process, then another cell could inject text into a running agent or answer its permission request, and holding the stdin pipe proves nothing. S8 measures it (decision 7). Outcomes: (a) the socket is absent or disabled by a flag or environment variable that only narrows the child (allowed; the adapter sets it, and 6.6's test asserts it); (b) the socket exists but accepts neither messages, interrupts nor responses and streams no events: go; (c) it accepts messages or interrupts but not a `control_response`: the approval hold stands, the injection residual is written into this item and goes to the user for acceptance before the adapter builds; (d) it accepts a `control_response`, or leaks the request ids and inputs: **slice 1 ships without the approval inbox** (the fail-closed path in decision 3, Permissions) and the approval design is reopened, because the hold would not bind. The adapter is not built until S8 has a recorded verdict. The remaining text of this item holds only under outcomes (a) to (c). The bridge never touches `/tmp/cc-socks` itself. The design still removes the hook-route, hook-token and `--bg` environment-delivery findings (M1, M2) for slices 1 to 3. The child's environment is an allowlist the bridge builds (item 6), and since the bridge spawns the child directly there is no supervisor to widen it; spike S1 plants a canary variable in the bridge's environment and checks it does not reach the child, and checks that the owner's login works with the allowlist alone. If login needs another variable, adding it is an ADR amendment, never a silent change, and an API key is never added (ADR 0001).
4. **Reads stay as ADR 0011 left them** (`/state`, `/events`, `/metrics` unauthenticated on loopback), with one narrowing: the snapshot carries only a tool name, a 200-character summary with secret-pattern matches masked (reuse the risk-check patterns), `inputLength` and `truncated`; *(round 2, F7)* the same mask and the same control and bidirectional-override escaping apply to **every** string a cell can influence that reaches the snapshot or the SSE stream: `approvals[].summary`, `cells[].tool.summary` (a running Bash tool's summary can hold a token), and the `note` and `reason` text of decisions and sessions lines; the full tool input is served only by the token-authenticated `GET /approvals/:id`. Residual risk, stated plainly: any local process or user can read the snapshot, including handoff text, cell ids and session ids (and so the `claude --resume` string), as today. This design assumes a single-user machine.
5. **Approval binding, the full-input rule, and the bare decision.**
   - An approval id is minted by the bridge, one-shot, bound to one cell and one request, and expires (default 10 minutes). A second decision on the same id returns 409. Expiry, bridge shutdown and a dead child answer deny.
   - **Allow requires the full input.** The 200-character summary can hide the dangerous tail of a padded command, so it is never the basis of an allow. The UI must fetch `GET /approvals/:id` and render the entire tool input (scrollable, never truncated) and its length before the `allow` control is enabled; `deny` is always enabled. The bridge enforces it too: `POST /approvals/:id` with `allow` returns 409 until a token-authenticated `GET /approvals/:id` has been served for that id (a test). The UI renders the input as text only, never HTML (React escaping plus ADR 0011's CSP), and shows control characters and bidirectional-override characters visibly (for example as `‮`), so they cannot reorder or hide text.
   - **The response is only ever a bare decision.** The encoder emits allow or deny with `reason` as plain text. If the protocol's allow response requires the tool input echoed back, the encoder returns the **original request input unchanged** (a test asserts deep equality), and it never emits `updatedPermissions` or any key that would persist or broaden a rule.
   - Ids for cells and approvals carry at least 64 random bits (16 hex characters; the examples above are that length).
   - **The decode contract** *(round 2, F3; the real shape from the S3 fixture, nested, not the flat shape in the 105 ticket comment)*: `{ type: "control_request", request_id, request: { subtype: "can_use_tool", tool_name, display_name, input, description, permission_suggestions: [{ type: "setMode", mode: "acceptEdits", destination: "session" }], tool_use_id } }`. `decodeControlRequest(obj)` returns an approval only when `type === "control_request"`, `request.subtype === "can_use_tool"`, `request.tool_name` is a non-empty string and `request.input` is a plain object; `request_id` must be a string of at most 128 characters and is treated as an **opaque key**, never parsed, never shown as an id: the host maps it to its own minted approval id. Anything else (another subtype, a missing or mistyped field, an array for `input`) is answered with a `control_response` of `behavior: "deny"` when a `request_id` string can be recovered, and is otherwise dropped; it is never allowed, and never reaches the UI as an approval. A second `control_request` with a `request_id` already held or already answered for that child is answered deny and creates no approval. `permission_suggestions` is **ignored** (it is the protocol's vehicle for broadening: a `setMode acceptEdits` suggestion would widen the session). The encoder emits only `behavior` (`allow` or `deny`), `reason`/`message` as plain text, and, for allow, `updatedInput` equal to the original `request.input` (S3's allow was honoured with exactly that; the deep-equality test stands). It never emits `updatedPermissions`, a mode or a rule. While the bridge holds an approval it never writes anything else about it to the child.
6. **Spawn safety.** Spawn with `spawn` and `shell: false`, never a shell string; the worktree is created with `execFile`. The child's environment is an allowlist (PATH, HOME, locale, `DEN_CLAUDE_BIN` if set), not a copy of the bridge's. The binary comes from `DEN_CLAUDE_BIN` or `claude` on PATH, never from a request. Worktree paths and branch names are derived server-side from validated `ref` and `cellType`; `ref` segments never start with `-`. Kill and message act only on cells in the host's live map, by `cellId`. No secret goes in argv. *(Round 2, F4:)* **The argument builder is a fixed template.** `buildClaudeArgs({ sessionId, agent, model? })` returns a list whose every element is either a literal flag or one of those three validated values (UUID pattern; role from the allowlist; model from a fixed list), plus the inline `--settings` JSON from 6.10. It has no `extraArgs`, `allowedTools` or other passthrough parameter, and rejects unknown input rather than ignoring it. The test asserts the **entire argv equals a known list** for a fixed input, that varying each allowed parameter changes only its own slot, and that no input shape (extra keys, a flag-shaped `agent`, a `--`-prefixed `model`) adds an element. The conformance script's `extraArgs` and `--allowedTools` are probe tooling and are not imported by the adapter. `--settings` carries only the bridge's own value.
7. **Caps.** At most 8 live daemon-spawned sessions regardless of policy; at most 20 pending approvals per cell (older ones expire first, answered deny); at most 2 KB per `message`; SSE keeps its 5 s back-pressure destroy. A cell that floods permission requests or output past the caps has its excess dropped and, past a hard limit, its child stopped.
8. **Cell output is untrusted.** Stdout lines (and transcript lines, if the tailer is on) are model and web-page text. The reader parses each line in try/catch and skips a bad one; caps a line at 1 MB and bounds its buffer when no newline arrives (drop and resync at the next newline); and treats every parsed string as text (never a path, a command or markup). A `control_request` whose shape does not parse is answered deny. If the transcript tailer is enabled it builds the path only from a sessionId matching the UUID pattern and checks with `realpath` that the result, and every sibling subagent file, stays under `~/.claude/projects`. Tests feed it malformed, oversize and path-traversal input.
9. **The registry is untrusted, and the bridge signals only its own children.** `.scratch/_run/sessions.jsonl` is writable by any cell. Replay validates every field (`cellId` against its pattern, `sessionId` as a UUID, `ref` against the dispatch regex, timestamps parseable) and drops what fails. The bridge sends signals only to `ChildProcess` objects it spawned in this run; no pid is ever read from a file, a request or the snapshot, so there is nothing to forge and no process-verification step is needed. The audit lines are tamper-evident only against the UI, not against a cell: a cell can append or edit them.
10. **A spawned cell can edit its own permission surface (partial measure, known gap).** The cell's worktree has its own `.claude/settings.json`, and an unattended cell can add `allow` rules there. The adapter passes the bridge's `deny` rule on `Write` and `Edit` of `.claude/**` as **inline JSON** in `--settings '{"permissions":{"deny":[...]}}'`, not a file *(round 2, F5: no file means no predictable path, no race and nothing a cell can edit; deny rules are not secrets, so argv is fine; if a file ever becomes unavoidable it is created under `mkdtemp` (0700) with the `wx` flag and the bridge never writes `~/.claude.json` or any Claude configuration)*. Whether `--settings` merges and a `deny` outranks a worktree `allow` is spike S6, **rerun as S6b in a real worktree under the repo** (round 2, F8; the first S6 ran in an untrusted temp directory and was unresolved, not failed: the CLI said it ignored the project's `permissions.allow` there because the workspace was not trusted, which says nothing about merge or precedence).
    - **Effective permissions are wider than the repo's allowlist** *(round 2, F5)*. S1's `system/init` showed the child loading the owner's user-scope MCP servers (blender, claude.ai connectors), plugins and user settings through `HOME`; user-level `allow` rules and hooks would apply to an unattended cell. The adapter therefore passes `--setting-sources project,local` and `--strict-mcp-config` with no `--mcp-config` (a role that needs an MCP server is a later amendment). S6b checks in `init` that `mcp_servers` and `plugins` carry no user-scope entries and that a user-level allow rule does not apply. `HOME` stays in the environment allowlist because login needs it, so a source that cannot be switched off this way (managed policy, a user hook) is a recorded residual, not a silent one.
    - **Trust is a user action, never bridge code** *(round 2, F8)*. If S6b shows that `.claude/worktrees/*` does not inherit the main checkout's trust (the project's `permissions.allow` is ignored there), the user accepts the trust dialog once in the repo, and that fact is recorded here in an ADR amendment. The bridge never writes trust into `~/.claude.json` (any cell can write that file). The untrusted case fails safe (more approvals, not fewer), so it is a usability cost, not a hole. Until S6b passes, no 106 test asserts deny-over-allow.
    - The fixtures to be committed under `apps/bridge/cells/fixtures/` need a **scrub step** before commit: init holds `cwd`, `memory_paths`, plugin paths (the owner's home path and username), `session_id`, `messaging_socket_path`, and plugin and MCP lists. Keep only the lines and keys the parser needs.
    - The bridge's own files: `.scratch/_run/` is created `0700`, `sessions.jsonl` `0600`, and any temp file the bridge writes goes under `mkdtemp`. These are hygiene, not a defence against a cell on the same account (decision 6, scope sentence). **This does not stop a Bash command from writing the file**, so it is a speed bump, not a wall; a real wall needs an OS sandbox, which is out of scope here (deferred, M6). One detection step stays in scope: slice 1 adds `.claude/**` to the `risk-check` patterns (`scripts/risk-check.mjs` has no `.claude` pattern today) so any such diff dispatches `security`. The posture otherwise matches interactive cells today, except these run unattended.
11. **Audit.** Every dispatch, decision and kill appends one line to `sessions.jsonl` with the route that acted. The token carries no session, so there is no "decision made without a UI session" to detect: what the line tells a reviewer is which route produced it. A forged decision would have to carry the UI token, which a cell does not have (item 2); there is no other route that can decide.

### 7. The thinnest first slice, and what follows

"Drive agent work from the UI" is reachable on day one with **slice 1 = dispatch + watch + approve + kill**, all over the one headless channel. Because dispatch starts a real `claude` child, "approve" here means both the dispatch click (a token-authenticated `POST /cells`) and the permission inbox.

- **How the bridge is started (open question for the user).** The bridge must run in a process that can reach the owner's `claude` login and is not inside a cell's sandbox (the probe's sandboxed child was "Not logged in"). The user cannot assume a terminal; options to settle, not decided here: the desktop app's own terminal, a double-click or login-item launcher script, or `npm run ui` in any shell. **The user starts the bridge; an agent's tool call never does** (round 2, F2: a launch URL printed into a cell's transcript is readable by any cell until it is spent or expires). Whatever is chosen must show the launch URL somewhere the user can see it and a cell cannot read, and must give the user a way to get a fresh launch code after a page reload without restarting the bridge (for example the user pressing Enter in the bridge's console). This ADR assumes no terminal.
- **Spikes first, each a go or no-go before building** (run with the owner's login, via `conformance.mjs`): **S1** a child spawned by a Node process with the allowlisted environment starts logged in, accepts `--session-id <uuid>` and `--agent <cell>` under `-p`, accepts a first stdin user message, emits `system/init` and exits on stdin EOF; the canary variable does not reach it. **S2** the stdout stream delivers a tool event in under one second, and shows whether subagent activity appears (decides the transcript tailer). **S3** `--permission-prompt-tool stdio` emits a `control_request` with the full tool input for a tool outside the allowlist, and a `control_response` allow and deny is honoured; capture the real shapes as fixtures. **S4** SIGTERM ends a running child, keeps the transcript, and `--resume <sessionId>` reopens it. **S5** billing: a five-hour usage reading before and after one trivial headless run, plus the account's usage page (decision 2); the user confirms the result. **S6** `--settings` merge and `deny` precedence over a worktree `allow` (6.10); its first run was **unresolved, not failed** (untrusted temp workspace), so S6b replaces it. If S1 fails because the owner's login does not reach a child of the bridge, slice 1 is blocked and goes back to the user (the fallback is a different process owner, not a different design here). If S3 fails, slice 1 ships without the inbox (decision 3, Permissions) and approval moves to slice 2.
- **Spike round 2 (S8, S4b, S6b, S3b)** *(security round 2)*. All run by the user with their own login through `conformance.mjs`, which ticket A extends (ids are case-insensitive on the command line: `--spike S8,S4b,S6b,S3b`). Each prints go, no-go or unconfirmed with evidence, saves fixtures with the owner's home path and username scrubbed, and spends about 8 to 12 turns on the cheap model in total. Nobody but the user runs them: a cell's sandbox has no login.
  - **S8, the child's messaging socket (F1; gates the adapter).** Spawn a child as S1 does, with `--permission-prompt-tool stdio` and a long allowed tool call available. (1) Read `messaging_socket_path` and `capabilities` from `system/init`; if absent or null, record it and stop (outcome a). (2) `stat` the socket and its directory: file type, mode, owner uid against this process's uid, and whether `others` have read or write (an open `/tmp/cc-socks` would also expose it to other OS users). (3) From a **separate plain `node:net` client** in the runner (a stand-in for any process on the account, using none of the child's pipes), connect and record whether it connects, any unsolicited bytes in 2 s (an event leak is a finding on its own), and any greeting. (4) Send probes as newline-delimited JSON and watch the child's **stdout** for an effect after each: (i) a user message carrying a random nonce, effect if an assistant line echoes the nonce; (ii) an interrupt (both `{type:"control_request",request:{subtype:"interrupt"}}` and `{type:"interrupt"}`) while a `sleep 15` tool call runs, effect if the tool result arrives early or errors; (iii) while a `can_use_tool` request for a write outside the allowlist is pending and **unanswered on stdin**, a `control_response` allow naming its real `request_id` over the socket, effect if the file appears. The runner then denies on stdin and ends the child. (5) If a socket existed, try disabling it: candidate flags from lines of `claude --help` matching `socket|messaging|inbound`, plus any `--s8-disable-flag <flag>` and `--s8-disable-env NAME=VALUE` the user supplies from their own reading (repeatable); a candidate counts only if `messaging_socket_path` is gone or the socket file absent **and** the child still logs in and answers. **Verdict:** go for outcomes (a) and (b) of 6.3, `residual` for (c) (messages or interrupts accepted, `control_response` not), no-go for (d), and `unconfirmed` (treated as no-go for the inbox) when the socket accepts a connection but the shapes tried show nothing either way. The evidence lists every shape tried, so `security` can judge how much silence proves.
  - **S4b, kill and exit during a tool call (F6).** Each run starts a child with `Bash(sleep 61)` allowed, asks it to run `sleep 61`, waits for the `tool_use` line plus 1.5 s, and records the child's pid and process group and the pids of every process whose command is `sleep 61` (`ps -axo pid,pgid,ppid,command`). (1) **EOF mid-call:** close stdin only, poll 15 s: did the child exit, and did the `sleep` survive? (2) **SIGTERM to the child alone:** exit time and `sleep` survival at +2 s and +10 s. (3) **SIGKILL to the child alone:** `sleep` survival. (4) If any `sleep` survived in (1) to (3), repeat (2) and (3) with the child spawned `detached: true` and the signal sent to the process group (`process.kill(-pid, ...)`). The runner always `SIGKILL`s leftover `sleep` pids it recorded at the end. **Verdict:** go (`decision: plain`) if the child exits on EOF mid-call and no `sleep` survives any run; go with `decision: group-kill` if survivors appear and the group signal clears them (decision 2 then requires the process-group spawn); no-go if survivors outlive the group signal, or if the child does not exit on EOF mid-call (the "bridge exit ends its cells" claim is then unproved and the shutdown handler is the only protection, which goes to the user).
  - **S6b, `--settings` precedence and setting sources in a real worktree (F5, F8).** `--repo <path>` (default: the repository containing the script) names a repo the owner has already trusted by running `claude` there interactively once; the script says so. It runs `git worktree add --detach <repo>/.claude/worktrees/s6b-<random> HEAD` and always removes it (`git worktree remove --force`) afterwards. In the worktree it writes `.claude/settings.local.json` with `permissions.allow` for `Write(allowed.txt)` and `Write(.claude/**)` and a probe role file, then spawns with the production-shaped arguments: `--setting-sources project,local`, `--strict-mcp-config`, and the deny rule as **inline JSON** in `--settings`. The prompt writes `allowed.txt` and then `.claude/probe.txt`. **Checks:** (1) `allowed.txt` exists (the project allow applied, so the worktree is trusted) and `.claude/probe.txt` does not (deny outranks allow, and inline `--settings` JSON merged rather than replaced); (2) stderr does not say the workspace is untrusted (if it does: verdict `unconfirmed` with the evidence that a worktree under `.claude/worktrees` does not inherit trust, which is the user's action to take and record, 6.10); (3) `init.mcp_servers` has no entry whose source is `user` or `claudeai`, and `init.plugins` has no user-scope plugin. **Verdict:** go needs (1) and (3); a failed (3) is no-go and the evidence names what leaked (a user-level allow rule or hook cannot be probed without editing the owner's settings, so it stays a stated residual).
  - **S3b (optional, never gating).** With the S3 setup: (1) a `Task` subagent that tries a tool outside the allowlist: does a `control_request` reach the parent's stdout, and does it identify the subagent? (If it does not, the tool ran or was denied without a prompt.) (2) one request left unanswered for `--s3b-wait <s>` (default 90): does the CLI time out, deny, or hang? (3) an allow response with `updatedInput` omitted: honoured or rejected? It records behaviour and returns `unconfirmed` when a question stays open; the adapter is built to 6.5 regardless.
  - The user copies the output directory (`results.json` and the scrubbed fixtures) to `.scratch/organism-infra/artifacts/106-conformance-<date>/` and says so on the board; the architect then records the verdicts in this ADR (an S8 outcome other than (a) or (b) needs a `security` re-review and the user's acceptance before the adapter's qa specify).
- **Slice 1 build order** *(security round 2: hardening cannot be last, because once the adapter lands any open mutating route starts a real `claude`)*. Six tickets, each under the ~120k-token split line of ADR 0019 decision 8: **A** the spike tooling (parallel to B and C1, touches only `apps/bridge/cells/conformance.*`); **B** the auth gate (route registry, Host, required Origin, Content-Type, body cap, `POST /session` and the launch code, Bearer, `POST /requests` retrofitted, the UI sending the token, the existing request tests and Approve and Reject buttons changed in the same ticket); **C1** the host core (`runtime.mjs` plus a fake, `host.mjs` dispatch policy, concurrency and caps, kill with escalation and the shutdown handler, `sessions.jsonl`, `POST /cells`, `POST /cells/:id/stop`, snapshot `cells` and the `cell` change, the `risk-check` pattern for `.claude/**`); **C2** approvals (the approval store, `GET` and `POST /approvals/:id`, expiry, the `GET`-before-`allow` gate, masking, snapshot `approvals` and the `approval` change; the host answers deny for anything it cannot decode); **D1** the adapter's pure half (the fixed argument builder, environment allowlist, `parseClaudeLine`, `decodeControlRequest` and the encoder, line caps, scrubbed fixtures); **D2** the adapter's process half (the child wrapper, kill and process-group handling per S4b, the shutdown wiring, the default runtime). B precedes C1, C1 precedes C2 and D1, and **D1 and D2 wait for the S8, S4b and S6b verdicts**. No mutating route merges before B. The pieces: `runtime.mjs` plus a fake; `claude-adapter.mjs` (spawn, stop, events, decide); `host.mjs` with dispatch policy, kill and the approval hold; the token and Origin hardening including `POST /requests`; `POST /cells`, `POST /cells/:id/stop`, `POST /approvals/:id`, `GET /approvals/:id`; snapshot `cells` and `approvals` and the `cell` and `approval` change types; `sessions.jsonl`; the `risk-check` pattern for `.claude/**`. The UI work (a "Run" button on the dispatch gate calling `POST /cells`, a stop button, cell tiles reading `cells[]`, the approval card that fetches the full input before enabling allow) belongs to the UI orchestrator; it needs only this ADR's JSON. The UI's existing Approve and Reject buttons call `POST /requests`, which now needs the token and Origin, so the bridge change and the UI change must land together or the existing buttons break.
- **Slice 2: message and hand over.** Spike S7 (a user message written to stdin during a running turn is queued rather than dropped or interrupting; the exact behaviour decides the UI wording). The `resume` string and a stop-then-resume hand-over flow.
- **Slice 3 (optional): direct relay-hop dispatch** of `developer`, `qa` and `security`, once the orchestrator's hop logic (SHA, Jev tier, verify depth) is a callable module rather than genome prose. Until then the orchestrator runs relays.
- **Later, optional: a `--bg` adapter mode** (decision 2), only if the user's environment allows it and cells need to outlive the bridge; needs its own security review.

**Considered options (designed twice).**

- *A (chosen). Bridge-owned headless processes: `claude -p` stream-json, in-process `send`, approvals over the stream (`control_request`).* The strongest control: a real `send`, an approval channel with no hook route and no hook token, children whose pipes only the bridge holds, no pid forging, and no dependence on `--bg`, which the user cannot use. It was the first draft's runner-up, rejected then for an undocumented permission protocol and the unconfirmed billing question; both remain true and are now handled as spikes S3 and S5 and an open question to the user, since the user constraint removes the alternative. Costs: cells end with the bridge; takeover is hand-over, not live pairing; the bridge process needs the owner's login.
- *B. Wake the orchestrator only; never spawn cells from the UI.* The thinnest possible, and what slice 1 does for relay tickets. Insufficient alone: the UI could not start a design or product cell, and could not kill one cell without ending the whole relay. Slice 1 therefore also spawns non-relay cells directly.
- *C (the first draft's choice, now an optional later mode). `CellRuntime` over `claude --bg`, an HTTP `PermissionRequest` hook for approvals, transcript tailing for state.* Cells would outlive the bridge and use only documented surfaces (`--bg`, `stop`, `attach`, HTTP hooks), but it adds an inbound route and token to defend and is unavailable in the user's desktop-app environment.
- *Interactive cells in a shared PTY with the daemon injecting keystrokes.* Rejected, as in the reference notes ("shared PTYs not adopted"): brittle against TUI changes and unsafe for approvals.
- *A WebSocket, a separate daemon port, a named pipe, or loopback HTTP with a token file.* Rejected in decisions 1 and 6.

**Conflicts with existing decisions (surfaced for the user).**

- **`CONTEXT.md` Gate request and ADR 0011 decision 6** say the UI does not execute and a Gate request never runs anything. This ADR has the bridge execute **steering commands** (dispatch, kill, message, permission decisions), but only when a token-authenticated route asks it to. A Gate request line still runs nothing, and **no cell ever starts because a line appeared**: the `dispatch-approve` line is an audit record the bridge writes after it handles `POST /cells`. Final rewording is in the Comments.
- **The 2026-09-28 event-source decision** (transcript tailing as the source, hooks as the fallback) is changed: the child's stdout stream is now the primary source, through the same parser; transcript tailing stays as a secondary feeder if S2 needs it, and the hook design stays only in the optional `--bg` mode. The user's reasons (one reader for animation and cost, no polling) still hold. Needs the user's acknowledgement.
- **ADR 0011 decision 1** says the daemon replaces `apps/bridge`. Amended: the bridge grows in place and no separate daemon exists. Decision 2's "zero Board write paths" is unchanged. ADR 0011's unauthenticated `POST /requests` is tightened to require the token and Origin.
- **ADR 0001** is consistent in letter for headless (CLI only, no SDK, no API key); the intent (plan usage) depends on the unconfirmed billing fact and the user's answer (decision 2, spike S5).
- **ADR 0004** is refined, not changed: the verbs stay; the interface is one `spawn` returning a cell process, `approve` becomes `decide` over an event, and `capabilities` is added (`attach` becomes `handover`, since live pairing is not offered).
- **ADR 0008 decision 8** is fulfilled by this ADR. **ADR 0007**'s `daemonStateSource` is this ADR's `cells[]` plus `cell` events, consumed by `snapshotStateSource`.
- **ADR 0002 and CLAUDE.md** disagree on the limit (one by default, `max_concurrent_cells: 2` now). This ADR reads the constant from `policy.mjs` and cites CLAUDE.md. ADR 0002's usage auto-pause may not see headless consumption (decision 2).

**Consequences.**

- Implementation tickets follow, in slice order; slice 1 is six tickets (decision 7, build order). The orchestrator writes them (`to-tickets`). The adapter tickets need the S8, S4b and S6b verdicts (run by the user with their login) before their qa specify; the auth gate and the host do not.

When the orchestrator should read the UI-woken prompt as approval, the existing "dispatch-approve acts as if the user answered in chat" step already covers it, with the forgery residual stated in decision 3; slice 3 would need a genome change, which only the orchestrator makes with the user's permission.
