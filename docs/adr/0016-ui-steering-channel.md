# The UI steers live cells through the bridge: SSE down, authenticated POST up, a `CellRuntime` adapter whose Claude implementation runs headless stream-json child processes the bridge owns, with a three-slice path from "dispatch, watch, approve, kill" to full steering

**Status:** accepted (user, 2026-09-30, in chat; drafted by the architect, 2026-10-01). It touches `apps/bridge`, `scripts/` and docs, so it crosses packages (an architect gate). **Amended in place twice (architect, 2026-10-01):** (1) after the first `security` review bounced decision 6 (handoff `11-security-2.md`): dispatch consent is bound to the UI token and approval requires the full tool input; the medium and low findings are folded in or deferred with a reason (decision 6, "Security review round 1"). (2) After a user constraint (via the orchestrator, 2026-10-01): the user runs from the Claude desktop app and cannot use `claude --bg`, so the primary Claude adapter is now headless `claude -p` stream-json children, not `--bg` sessions, and nothing assumes a terminal-started bridge (decisions 2, 3, 6, 7). **Still open:** `security` must re-review the twice-amended decision 6 before slice 1 builds the auth code; the billing facts for headless runs are unconfirmed (see decision 2); and the domain terms and Gate request rewording await `CONTEXT.md` (final text in Comments; the user asked for it to be added).

**Context.** Ticket `organism-infra/11` asks for the channel that lets the UI watch and steer live cells: an inbox for tool-permission requests, taking over or pairing, a message mid-task, kill, and sub-second live state. ADR 0008 decision 8 left it open; ADR 0004 fixed only the adapter's verbs (spawn, stream events, send message, approve/deny, stop). The user's goal (2026-09-30) is to drive agent work from the UI within a day, so this ADR also names the thinnest first slice. Facts that shape the design:

- Today the UI cannot reach a cell. Cells are subagents the orchestrator launches with its Agent tool inside an interactive desktop-app session; nothing outside that session holds a handle to them.
- The bridge (ADR 0011) already serves `GET /state`, an SSE `GET /events`, and `POST /requests`, behind a loopback bind and Host/Origin/Content-Type checks. The bridge has no Board write path, and a Gate request "never runs anything itself" (`CONTEXT.md`).
- The user decided on 2026-09-28 that the event source is transcript tailing (`~/.claude/projects/<cwd>/<session>.jsonl` plus the subagent transcripts beside it), one reader for tool-call animation and cost, with the hook design as a fallback. This ADR changes the primary source to the child's own stdout stream (same line shape, same parser); see Conflicts.
- ADR 0001: cells are unmodified `claude` CLI processes on the owner's login; no model API, no Agent SDK.
- **The user works from the Claude desktop app and cannot use `claude --bg`** (user constraint relayed by the orchestrator, 2026-10-01). The bridge therefore cannot rely on background sessions, `claude agents`, `claude attach` or `claude stop`, and cannot assume it was started from a terminal.
- The installed CLI (2.1.284, checked with `--help` for the first draft) has headless `claude -p --input-format stream-json --output-format stream-json` and `--permission-prompt-tool`, `--session-id`, `--resume`, `--settings`, `--agent`.
- Evidence gathered (a throwaway probe in the architect's scratchpad, plus a `scout` read of the official docs; not committed). Proved: the binary accepts the stream-json flags and `--permission-prompt-tool stdio`, and emits `system/init` with `session_id` in about 0.5 s. Not proved: any model-backed behaviour. A `claude` spawned from the architect's sandbox answers "Not logged in", so the permission request and response shapes, the stdin user-message shape, mid-turn messages and `--agent` under `-p` are all unverified here. From the docs: `--resume <id>` reopens a session; SIGTERM leaves a turn unfinished; the `--permission-prompt-tool` request/response shape is undocumented. The same support article (as read by `scout`, 2026-10-01) says `claude -p` usage has drawn from a separate monthly credit instead of plan usage since 2026-06-15. That is unconfirmed (see decision 2).

**Decision.**

### 1. Transport: the bridge grows in place; SSE down, POST up

The UI talks to the existing bridge process over its existing localhost HTTP surface. There is no separate daemon process and no second port. ADR 0011 said the daemon would later replace `apps/bridge` behind the same surface; this decision makes that literal: `apps/bridge` gains a `cells/` module and stays the one process the user starts. `organism-infra/03` (board IPC) stays parked under ADR 0008 decision 5; this ADR does not revive it.

- **Down (cell state to the UI):** the same SSE stream (`GET /events`). New additive snapshot keys and `change` types (decision 4). Sub-second delivery needs no polling: a cell event reaches the stream as soon as the child's stdout line is parsed.
- **Up (commands to the daemon):** `POST` JSON routes (decision 3), each one command, each answered with 200/201 or a 4xx that names the refusal.

Why not a WebSocket: the traffic is low-rate commands up and a firehose down, which SSE plus POST already model. A WebSocket handshake is not covered by CORS, so it would need its own Origin enforcement, and framing needs a dependency (`ws`) or hand-rolled code. SSE plus POST reuses ADR 0011's tested hardening (Host check, Content-Type, Origin, body caps, SSE back-pressure destroy) unchanged and adds no dependency. Why not a named pipe or Unix socket: a browser cannot open one (ADR 0008 decision 8). Why not a second "daemon" port: it would double the exposure surface for no capability.

### 2. How a steering command reaches a live cell: `CellRuntime` (refines ADR 0004)

One module interface, `apps/bridge/cells/runtime.mjs`. ADR 0004's verbs, made concrete: a runtime spawns a **cell process**, and each live cell is one such object, so the interface stays small and the host owns the handle map. A capability set lets a runtime say what it cannot do (the lowest-common-denominator rule):

```
CellRuntime = {
  id: "claude",
  capabilities: { spawn, stop, approve, send, handover },     // booleans; the UI greys out what is false
  spawn({ cellType, mode?, ref, cwd, prompt, model?, sessionId, resume? }) -> Promise<CellProcess>
}
CellProcess = {
  handle,                                            // opaque string; key in the host's map
  events: AsyncIterable<CellEvent>,                  // tool start/end, message, usage, permission-request, state, done
  stop() -> Promise<void>,
  send?(text) -> Promise<void>,
  decide?(requestId, { allow, reason? }) -> Promise<void>,   // answers a held permission request
  resumeCommand?() -> string                         // shown to the user; the bridge never runs it
}
```

The adapter builds the child's environment itself (an allowlist, decision 6.6), so it is not a parameter. `startBridge({ root, port, uiDir, runtime })` takes the runtime as a parameter, defaulting to the Claude adapter. Tests pass a fake runtime. Two adapters (Claude, fake) make this a real seam.

How the **Claude adapter** carries each command (the answer to "hooks, stdin, signals"). The bridge spawns `claude` as its own child with piped stdio and holds the pipes, so there is no inbound network route from a cell:

| Command | Mechanism | Slice |
|---|---|---|
| Dispatch | create a worktree, then spawn `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio --session-id <uuid> --agent <cell> --settings <file>` with cwd in it; the prompt is the first stdin user message; the bridge mints the session id | 1 |
| Watch | parse the child's stdout stream-json lines into `CellEvent`s with `parseClaudeLine` | 1 |
| Kill | close stdin, then SIGTERM on the `ChildProcess` the bridge itself spawned this run (the conversation is kept and `--resume` reopens it); never a pid from a file or a request | 1 |
| Approve or deny a tool permission | the CLI writes a `control_request` (permission check) on stdout; the host holds it as an approval until the UI decides, then writes the matching `control_response` on stdin. Timeout, expiry or bridge shutdown answers **deny** | 1 (if spike S3 passes; else slice 2) |
| Message mid-task | write a user message line on the child's stdin | 2 |
| Take over or pair | **hand over**, not pair: stop the child, then the UI shows `claude --resume <sessionId>` for the user's terminal, run in the cell's cwd. Two live processes never share a session. Live pairing is not offered | 2 |

The exact shapes of the stdin user message, the `control_request` and the `control_response` are undocumented and unverified; spikes S1 to S3 fix them before slice 1 builds. Nothing outside `cells/claude-adapter.mjs` may name a Claude flag or message shape.

**Process lifetime.** Children belong to the bridge: a child is not detached, and closing its stdin or SIGTERM ends it. If the bridge exits, its cells end (spike S4 confirms the child exits on stdin EOF). Cells do not survive a bridge restart; on start the host marks previously live cells `terminated` with reason `bridge-restart`, and the UI can offer the `claude --resume` command. This is the cost of owning the pipes; it removes the pid-reconciliation and process-verification problems of a detached design.

**Background sessions are an optional later adapter mode, not part of slices 1 to 3.** `claude --bg` plus an HTTP `PermissionRequest` hook would let cells outlive the bridge, but the user cannot use it now. If adopted, it needs its own security review, because it adds an inbound hook route and a hook token. The requirements from review round 1 carry over to it: an `Origin` exemption for the hook route with a Host check, a per-session hook token (at least 128 bits) delivered by environment only, never argv or a file, with a canary spike proving the environment allowlist holds under `--bg` (a background session may take its environment from the CLI's supervisor); a 256 KB body cap; the UI token rejected on the hook route and the hook token on every UI route; and a registry-pid kill fallback only after verifying the process command line and start time.

**Billing and ADR 0001 (open question; not asserted).** Headless `claude -p` is still the unmodified CLI on the owner's login: no SDK package, no API key, no model API, so it satisfies the letter of ADR 0001. Whether it satisfies the intent (cells run on the owner's plan usage) depends on a fact nobody here has confirmed: the support article read by `scout` says `claude -p` usage has drawn from a separate monthly credit since 2026-06-15. If that is true, daemon-spawned cells would be metered apart from the interactive session, the usage guard (which reads plan usage) would not see their consumption, and ADR 0001 and ADR 0002's auto-pause would need amending. If it is false, nothing changes. This ADR neither assumes nor rules out either answer. Spike S5 measures it (a plan-usage reading before and after one trivial headless run, plus the account's usage page), and the user confirms. Until the user does, slice 1 may be built and exercised on trivial prompts, but headless dispatch is not adopted as the default way to run relays.

Fail-closed rule for every adapter: a permission request with no decision (timeout, expiry, bridge shutdown, hostile or unparseable request) is answered deny or left unanswered by a dead child. The bridge never auto-allows.

**One line parser, one source.** Transcript lines and stream-json stdout lines share the message shape (`message.content` blocks, `message.usage`). `parseClaudeLine(line) -> CellEvent[]` is that one parser. The child's stdout feeds it directly; this keeps the user's "one reader feeds animation and cost" decision, with a pipe instead of a file. A transcript tailer (an `fs.watch` incremental read of `~/.claude/projects/<cwd>/<session>.jsonl` and its sibling subagent files) is kept as a secondary feeder, enabled only if spike S2 shows the stdout stream omits subagent activity. Pipe latency should be well under a second; unverified, S2 measures it. Permission requests arrive on the same stream and do not depend on the tailer. Cell output is untrusted text; the input rules are decision 6.8.

### 3. Routes and the `CellHost` module

Behind the routes sits one deep module, `CellHost` (`apps/bridge/cells/host.mjs`). The routes are thin; the module owns the policy, the live-cell map, the registry and the event merge.

| Route | Body | Does |
|---|---|---|
| `POST /cells` | `{ ref, cellType, mode? }` | dispatch (below); **the only way a cell starts**; Bearer token |
| `POST /requests` | ADR 0011's Gate request body | records an audit line; runs nothing; now Bearer token and required Origin (decision 6.1) |
| `POST /cells/:id/stop` | none | kill |
| `POST /cells/:id/message` | `{ text }` (at most 2 KB) | send (slice 2) |
| `POST /approvals/:id` | `{ decision: "allow" \| "deny", note? }` | answer a permission request |
| `GET /approvals/:id` | none | the full tool input for a pending request, token required |

There is no inbound hook route: permission traffic rides the child's pipes, never the network.

**Dispatch policy** (all refusals write nothing and start nothing):
- **Consent is the token, not a file line.** A cell starts only from a Bearer-token `POST /cells`. The bridge never starts a cell because it saw a `dispatch-approve` line, whether that line arrived through `POST /requests` or was appended straight to `.scratch/_requests/requests.jsonl` by a process on the same account (any cell can do that). The Run button calls `POST /cells`; the bridge itself then appends the `dispatch-approve` line (with `outcome: "dispatched <cellId>"`, ADR 0011 decision 6's append-only form) as an **audit record, not proof**: a line in that file proves nothing about who wrote it.
- `ref` names a ticket in the snapshot with `gate == "dispatch"` (ADR 0011 decision 3).
- **Known residual (not closed here):** the orchestrator genome (step 2) still reads `requests.jsonl` and treats a `dispatch-approve` line as the user's answer, so a prompt-injected cell can forge a line and talk the orchestrator into acting. This is the same posture as before this ADR, and no UI token defends it, because the orchestrator cannot verify who wrote a line. Follow-up ticket proposed: bridge-signed request lines (the bridge appends an HMAC under a key the cells cannot read) plus an orchestrator genome change to accept only signed lines; the genome edit is the orchestrator's to make with the user's permission.
- `cellType` is one of the nine known cells. **Slice 1 dispatches only `orchestrator` and the non-relay cells (`architect`, `product`, `designer`, `scout`).** Relay-hop cells (`developer`, `qa`, `security`) are refused with 409 "dispatch the orchestrator": the orchestrator owns the hop SHA, the Jev tier and the verify depth, and re-implementing that in the bridge would fork the relay.
- `orchestrator` runs in the main checkout (as it does today) with a daemon-built prompt that cites the request id and says to read it with `scripts/requests.mjs --list`. Non-relay cells get a detached worktree under `.claude/worktrees/<cell>-<NN>-<shortid>` at the main `HEAD`, and a prompt whose first command is the same `node scripts/cell-start.mjs --base <sha> --branch <cell>/<NN>-<slug> --ticket <ref> --cell <cell>` line the orchestrator writes today. The prompt is a fixed template filled only with validated fields (`ref` matches `^[a-z0-9][a-z0-9-]*/\d{2}-[a-z0-9][a-z0-9-]*$`, so no segment starts with `-`; `cellType` from the allowlist); no client string reaches it. If `--agent <cell>` is not honoured under `-p` (spike S1), the template's first line tells the cell to read `.claude/agents/<cell>.md` and follow it, which `CLAUDE.md` already allows.
- Concurrency: refuse when running daemon-spawned cells would exceed `max_concurrent_cells` (2 per CLAUDE.md, ADR 0002; one constant in `cells/policy.mjs`). The check and the live-map reservation (one live cell per `ref`, the live-count slot, the 8-session cap) are **one synchronous step** with no `await` between them, so two near-simultaneous clicks cannot both pass; a test fires two `POST /cells` concurrently with one slot left. Usage: refuse at a five-hour reading of 90% or more (ADR 0002's auto-pause). A `null` reading allows the dispatch and says so in the response. (If headless runs draw from a separate credit pool, this reading does not see them; see decision 2.)
- Permissions: the daemon passes **no** permission-broadening flag, ever (`--dangerously-skip-permissions`, `--permission-mode bypassPermissions` and `--allow-dangerously-skip-permissions` are not constructible by the adapter; a test asserts the argument builder). Spawned cells use the repo's own `.claude/settings.json` allowlist plus a bridge-generated `--settings` deny rule on writes to `.claude/**` (decision 6.10, a partial measure). A tool outside the allowlist becomes a pending approval in the UI (slice 1, if S3 passes). If S3 fails, the adapter omits `--permission-prompt-tool`, the CLI denies unlisted tools on its own, and the cell reports the failure.
- Board: the bridge still has zero Board write paths (ADR 0011). The spawned cell claims, comments and releases through `board`, as today.

### 4. State the UI sees (additive keys on ADR 0011's snapshot)

```json
{
  "cells": [{
    "id": "c-7f3a19d04be2c685", "ref": "organism-infra/11-daemon-ui-cell-channel-design", "cellType": "architect",
    "mode": null, "runtime": "claude", "sessionId": "08376463-453a-4135-a7df-4ee921c22e86",
    "state": "working", "startedAt": "2026-10-01T09:00:00.000Z", "lastEventAt": "2026-10-01T09:03:12.410Z",
    "tool": { "name": "Read", "summary": "docs/adr/0011-..." },
    "tokens": { "input": 41200, "output": 3100 },
    "capabilities": { "stop": true, "approve": true, "send": false, "handover": true },
    "resume": null
  }],
  "approvals": [{
    "id": "a-91d07c3e5b2a4f68", "cellId": "c-7f3a19d04be2c685", "tool": "Bash", "summary": "npm test (first 200 chars, secrets masked)",
    "inputLength": 1840, "truncated": true,
    "ts": "2026-10-01T09:03:12.410Z", "expiresAt": "2026-10-01T09:13:12.410Z", "state": "pending"
  }]
}
```

- `resume` is `null` while the child runs; once the cell is stopped, done or terminated it is `claude --resume <sessionId>` (a string for the user's terminal; the bridge never runs it).
- **`summary` is a display hint, never the basis of an allow.** It is capped at 200 characters, so a padded command can hide its tail past the cut. The snapshot therefore also carries `inputLength` and `truncated`, and the allow action is gated on the full input (decision 6.5): the UI must fetch `GET /approvals/:id` and render the whole input before `allow` is enabled; `deny` is always enabled.
- `state` is one of the director's `STATES` (ADR 0007): `working`, `waiting_on_user` (a permission is pending or the session is idle awaiting input), `blocked`, `done`, `failed`, `throttled`, `terminated` (killed by the user, or ended by a bridge restart), `idle`. `snapshotStateSource` (ADR 0011 decision 7) can key off it directly, so nothing new is animated.
- `change` types added: `cell` (full object, or `null` when it leaves), `approval` (full object). Same `seq` rules as ADR 0011 decision 5; unknown types stay ignored.
- `tool` and `tokens` come from the line parser. Cost-pricing and the telemetry reader are a separate ticket; this ADR only fixes that the same parser feeds them.
- Registry persistence: an append-only `.scratch/_run/sessions.jsonl` (spawn, decision, stop; one line each, with `ts`, `cellId`, `ref` and, for decisions, the request id and the acting route). On start the host replays it for history and marks cells that were live as `terminated` (decision 2, process lifetime). `.scratch/_run/` should be git-ignored; the developer adds that line to `.gitignore`. **The file is untrusted input** (any cell can write it, same account): replay validates every field (decision 6.9), drops lines that fail, and nothing read from it is ever signalled or executed.

### 5. Test seams

Two, at the highest points:

1. **`startBridge` over HTTP, with a fake `runtime` injected.** Dispatch validation and refusals, concurrency and usage limits, auth rejections, kill, the permission round-trip (the fake emits a permission request, `POST /approvals/:id` releases it with the right response, timeout answers deny), the SSE `cell` and `approval` events, bridge-restart marking, and the security assertions in decision 6 (token and Origin on every mutating route including `POST /requests`; a forged `requests.jsonl` line or `POST /requests` starts nothing; `OPTIONS` carries no `Access-Control-Allow-*`; `allow` refused until the full input was served; the concurrent-dispatch race). The existing `bridge-*.test.mjs` fixtures extend.
2. **`claude-adapter.mjs` as pure functions over fake pipes:** the argument builder (including the "no permission-broadening flag" and "no secret in argv" assertions), `parseClaudeLine` over recorded lines plus hostile ones (malformed JSON, oversize line, no newline), the `control_request` decode and `control_response` encode (decision 6.5), and the child-process wrapper driven by a stub script that speaks the stream. Fixtures are real captured lines, committed under `apps/bridge/cells/fixtures/`. If the transcript tailer is enabled, its path builder joins this seam.

The adapter against a real `claude` is a manual conformance script (`apps/bridge/cells/conformance.mjs`), not a CI test, because it needs the owner's login, which a cell's sandbox does not have. The user (or a developer working in a session that has the login) runs it; slice 1's first task is to run it (spikes below).

### 6. Auth and exposure (`security` reviews this section)

Threat model, in order of likelihood: (a) a web page in the user's browser firing requests at localhost (CSRF, DNS rebinding); (b) **a cell itself** (an agent, possibly prompt-injected) running `curl` against the bridge, or writing files on the same account, to approve its own permission request, dispatch, or kill another cell; (c) another local OS user on a shared machine; (d) malformed or hostile cell output (stdout or transcript lines).

The principle that follows from (b): **the UI token is the only proof of user intent.** A file line, a snapshot id or an unauthenticated request proves nothing, because a cell can produce all three.

1. **Bind, Host, Origin, preflight.** Loopback `127.0.0.1` only, not configurable (ADR 0011). Every route keeps the Host check. Every mutating route (`POST /cells`, `POST /cells/:id/stop`, `POST /cells/:id/message`, `POST /approvals/:id`, **and `POST /requests`**) additionally **requires** an `Origin` header equal to `http://127.0.0.1:<port>` or `http://localhost:<port>` (a browser always sends one on a cross-site POST; ADR 0011 only checked it when present), `Content-Type: application/json`, a valid Bearer token (item 2), and the 4 KB body cap. `GET /approvals/:id` needs the token too. Failures return 403 or 401 and write nothing. There is no exemption and no hook route: permission traffic never crosses the network (item 3). `OPTIONS` on any mutating route returns no `Access-Control-Allow-*` header. If the Vite dev origin is ever allowed, it is one exact allowlist entry, never a pattern. Tests assert each of these.
2. **Per-run UI token.** The bridge generates 32 random bytes at start, keeps them **in memory only** (not on disk, not in the environment of anything it spawns), and prints one launch URL with the token in the fragment: `http://127.0.0.1:4317/#token=<...>`. The URL goes to the bridge's own console output only: it is never passed in argv (for example to `open <url>`, which `ps` shows), never written to a log or file. How the user reaches that console when the bridge is not started from a terminal is an open question (decision 7, "How the bridge is started"). The UI reads the fragment, removes it from the address bar, keeps the token in memory, and sends `Authorization: Bearer <token>` on every route in item 1. A custom header also forces a CORS preflight the bridge never answers, which stops cross-origin scripts even if the Origin check had a hole. The comparison hashes both sides with sha256 and uses `crypto.timingSafeEqual` on the digests (the raw call throws on unequal lengths); any failure, including a malformed header, returns 401, never 500. Why not write the token to a file: a cell runs as the same OS user and can read any 0600 file the user can, which defeats threat (b). A cell also cannot find it in the bridge's environment because there is none. **Scope, said plainly:** the token gates the bridge, not the operating system. A process on the same account can still signal another process it can see; this ADR does not close that.
3. **No inbound permission route; the channel is the child's pipes.** Because the bridge owns each cell's stdin and stdout, a cell cannot submit a permission request or a decision over the network, and no hook token exists. A cell can only write to its own stdout, which the bridge treats as untrusted text (item 8). A permission request gets a bridge-minted approval id bound to that child; no other process can answer it, because only the bridge holds the child's stdin. This removes the hook-route, hook-token and `--bg` environment-delivery findings (M1, M2) for slices 1 to 3. The child's environment is an allowlist the bridge builds (item 6), and since the bridge spawns the child directly there is no supervisor to widen it; spike S1 plants a canary variable in the bridge's environment and checks it does not reach the child, and checks that the owner's login works with the allowlist alone. If login needs another variable, adding it is an ADR amendment, never a silent change, and an API key is never added (ADR 0001).
4. **Reads stay as ADR 0011 left them** (`/state`, `/events`, `/metrics` unauthenticated on loopback), with one narrowing: the snapshot carries only a tool name, a 200-character summary with secret-pattern matches masked (reuse the risk-check patterns), `inputLength` and `truncated`; the full tool input is served only by the token-authenticated `GET /approvals/:id`. Residual risk, stated plainly: any local process or user can read the snapshot, including handoff text, cell ids and session ids (and so the `claude --resume` string), as today. This design assumes a single-user machine.
5. **Approval binding, the full-input rule, and the bare decision.**
   - An approval id is minted by the bridge, one-shot, bound to one cell and one request, and expires (default 10 minutes). A second decision on the same id returns 409. Expiry, bridge shutdown and a dead child answer deny.
   - **Allow requires the full input.** The 200-character summary can hide the dangerous tail of a padded command, so it is never the basis of an allow. The UI must fetch `GET /approvals/:id` and render the entire tool input (scrollable, never truncated) and its length before the `allow` control is enabled; `deny` is always enabled. The bridge enforces it too: `POST /approvals/:id` with `allow` returns 409 until a token-authenticated `GET /approvals/:id` has been served for that id (a test). The UI renders the input as text only, never HTML (React escaping plus ADR 0011's CSP), and shows control characters and bidirectional-override characters visibly (for example as `‮`), so they cannot reorder or hide text.
   - **The response is only ever a bare decision.** The encoder emits allow or deny with `reason` as plain text. If the protocol's allow response requires the tool input echoed back, the encoder returns the **original request input unchanged** (a test asserts deep equality), and it never emits `updatedPermissions` or any key that would persist or broaden a rule.
   - Ids for cells and approvals carry at least 64 random bits (16 hex characters; the examples above are that length).
6. **Spawn safety.** Spawn with `spawn` and `shell: false`, never a shell string; the worktree is created with `execFile`. The child's environment is an allowlist (PATH, HOME, locale, `DEN_CLAUDE_BIN` if set), not a copy of the bridge's. The binary comes from `DEN_CLAUDE_BIN` or `claude` on PATH, never from a request. Worktree paths and branch names are derived server-side from validated `ref` and `cellType`; `ref` segments never start with `-`. Kill and message act only on cells in the host's live map, by `cellId`. No secret goes in argv.
7. **Caps.** At most 8 live daemon-spawned sessions regardless of policy; at most 20 pending approvals per cell (older ones expire first, answered deny); at most 2 KB per `message`; SSE keeps its 5 s back-pressure destroy. A cell that floods permission requests or output past the caps has its excess dropped and, past a hard limit, its child stopped.
8. **Cell output is untrusted.** Stdout lines (and transcript lines, if the tailer is on) are model and web-page text. The reader parses each line in try/catch and skips a bad one; caps a line at 1 MB and bounds its buffer when no newline arrives (drop and resync at the next newline); and treats every parsed string as text (never a path, a command or markup). A `control_request` whose shape does not parse is answered deny. If the transcript tailer is enabled it builds the path only from a sessionId matching the UUID pattern and checks with `realpath` that the result, and every sibling subagent file, stays under `~/.claude/projects`. Tests feed it malformed, oversize and path-traversal input.
9. **The registry is untrusted, and the bridge signals only its own children.** `.scratch/_run/sessions.jsonl` is writable by any cell. Replay validates every field (`cellId` against its pattern, `sessionId` as a UUID, `ref` against the dispatch regex, timestamps parseable) and drops what fails. The bridge sends signals only to `ChildProcess` objects it spawned in this run; no pid is ever read from a file, a request or the snapshot, so there is nothing to forge and no process-verification step is needed. The audit lines are tamper-evident only against the UI, not against a cell: a cell can append or edit them.
10. **A spawned cell can edit its own permission surface (partial measure, known gap).** The cell's worktree has its own `.claude/settings.json`, and an unattended cell can add `allow` rules there. The adapter passes a bridge-generated `--settings` file (written by the bridge outside the worktree, per session, removed on stop) with a `deny` rule on `Write` and `Edit` of `.claude/**`; whether `--settings` merges and a `deny` outranks a worktree `allow` is spike S6. **This does not stop a Bash command from writing the file**, so it is a speed bump, not a wall; a real wall needs an OS sandbox, which is out of scope here (deferred, M6). One detection step stays in scope: slice 1 adds `.claude/**` to the `risk-check` patterns (`scripts/risk-check.mjs` has no `.claude` pattern today) so any such diff dispatches `security`. The posture otherwise matches interactive cells today, except these run unattended.
11. **Audit.** Every dispatch, decision and kill appends one line to `sessions.jsonl` with the route that acted. The token carries no session, so there is no "decision made without a UI session" to detect: what the line tells a reviewer is which route produced it. A forged decision would have to carry the UI token, which a cell does not have (item 2); there is no other route that can decide.

**Security review round 1 (handoff `11-security-2.md`), where each finding landed.** H1: decision 3 (consent), 6.1 (`POST /requests`), Conflicts; residual named. H2: decisions 4, 6.5. M1 and M2 (hook route and `--bg` env delivery): dissolved by the headless design (6.3); the requirements carry over to the optional `--bg` mode (decision 2). M3: 6.9, simplified. M4: 6.8. M5: 6.5, adapted to the stdio response. M6: 6.10, **partially deferred**: the real fix (an OS sandbox or write-protecting the worktree's `.claude/`) is a separate ticket, because it changes how every cell runs, not just daemon-spawned ones. L1 to L3: 6.2, 6.5. L4: decision 3 concurrency. L5: decision 3 regex, 6.6. L6: 6.2 scope sentence, 6.11. L7: 6.1. Open for the developer rather than the ADR: the stdio message shapes (S1, S3), the `--settings` merge behaviour (S6), and the wording of the UI's "view full input" control (the UI orchestrator). The review's secret scan used a pattern grep because `gitleaks` was missing from PATH; it is installed at `/opt/homebrew/bin/gitleaks`, so the re-review can run it.

### 7. The thinnest first slice, and what follows

"Drive agent work from the UI" is reachable on day one with **slice 1 = dispatch + watch + approve + kill**, all over the one headless channel. Because dispatch starts a real `claude` child, "approve" here means both the dispatch click (a token-authenticated `POST /cells`) and the permission inbox.

- **How the bridge is started (open question for the user).** The bridge must run in a process that can reach the owner's `claude` login and is not inside a cell's sandbox (the probe's sandboxed child was "Not logged in"). The user cannot assume a terminal; options to settle, not decided here: the desktop app's own terminal, a double-click or login-item launcher script, or `npm run ui` in any shell. Whatever is chosen must show the launch URL with the token somewhere the user can see it and a cell cannot read. This ADR assumes no terminal.
- **Spikes first, each a go or no-go before building** (run with the owner's login, via `conformance.mjs`): **S1** a child spawned by a Node process with the allowlisted environment starts logged in, accepts `--session-id <uuid>` and `--agent <cell>` under `-p`, accepts a first stdin user message, emits `system/init` and exits on stdin EOF; the canary variable does not reach it. **S2** the stdout stream delivers a tool event in under one second, and shows whether subagent activity appears (decides the transcript tailer). **S3** `--permission-prompt-tool stdio` emits a `control_request` with the full tool input for a tool outside the allowlist, and a `control_response` allow and deny is honoured; capture the real shapes as fixtures. **S4** SIGTERM ends a running child, keeps the transcript, and `--resume <sessionId>` reopens it. **S5** billing: a five-hour usage reading before and after one trivial headless run, plus the account's usage page (decision 2); the user confirms the result. **S6** `--settings` merge and `deny` precedence over a worktree `allow` (6.10). If S1 fails because the owner's login does not reach a child of the bridge, slice 1 is blocked and goes back to the user (the fallback is a different process owner, not a different design here). If S3 fails, slice 1 ships without the inbox (decision 3, Permissions) and approval moves to slice 2.
- **Slice 1 build:** `runtime.mjs` plus a fake; `claude-adapter.mjs` (spawn, stop, events, decide); `host.mjs` with dispatch policy, kill and the approval hold; the token and Origin hardening including `POST /requests`; `POST /cells`, `POST /cells/:id/stop`, `POST /approvals/:id`, `GET /approvals/:id`; snapshot `cells` and `approvals` and the `cell` and `approval` change types; `sessions.jsonl`; the `risk-check` pattern for `.claude/**`. The UI work (a "Run" button on the dispatch gate calling `POST /cells`, a stop button, cell tiles reading `cells[]`, the approval card that fetches the full input before enabling allow) belongs to the UI orchestrator; it needs only this ADR's JSON. The UI's existing Approve and Reject buttons call `POST /requests`, which now needs the token and Origin, so the bridge change and the UI change must land together or the existing buttons break.
- **Slice 2: message and hand over.** Spike S7 (a user message written to stdin during a running turn is queued rather than dropped or interrupting; the exact behaviour decides the UI wording). The `resume` string and a stop-then-resume hand-over flow.
- **Slice 3 (optional): direct relay-hop dispatch** of `developer`, `qa` and `security`, once the orchestrator's hop logic (SHA, Jev tier, verify depth) is a callable module rather than genome prose. Until then the orchestrator runs relays.
- **Later, optional: a `--bg` adapter mode** (decision 2), only if the user's environment allows it and cells need to outlive the bridge; needs its own security review.

**Considered options (designed twice).**

- *A (chosen). Bridge-owned headless processes: `claude -p` stream-json, in-process `send`, approvals over the stream (`control_request`).* The strongest control: a real `send`, an approval channel with no hook route and no hook token, children whose pipes only the bridge holds, no pid forging, and no dependence on `--bg`, which the user cannot use. It was the first draft's runner-up, rejected then for an undocumented permission protocol and the unconfirmed billing question; both remain true and are now handled as spikes S3 and S5 and an open question to the user, since the user constraint removes the alternative. Costs: cells end with the bridge; takeover is hand-over, not live pairing; the bridge process needs the owner's login.
- *B. Wake the orchestrator only; never spawn cells from the UI.* The thinnest possible, and what slice 1 does for relay tickets. Insufficient alone: the UI could not start a design or product cell, and could not kill one cell without ending the whole relay. Slice 1 therefore also spawns non-relay cells directly.
- *C (the first draft's choice, now an optional later mode). `CellRuntime` over `claude --bg`, an HTTP `PermissionRequest` hook for approvals, transcript tailing for state.* Cells would outlive the bridge and use only documented surfaces (`--bg`, `stop`, `attach`, HTTP hooks), but it adds an inbound route and token to defend and is unavailable in the user's desktop-app environment.
- *Interactive cells in a shared PTY with the daemon injecting keystrokes.* Rejected, as in the reference notes ("shared PTYs not adopted"): brittle against TUI changes and unsafe for approvals.
- *A WebSocket, a separate daemon port, a named pipe, or loopback HTTP with a token file.* Rejected in decisions 1 and 6.

**Conflicts with existing decisions (surfaced for the user).**

- **`CONTEXT.md` Gate request and ADR 0011 decision 6** say the UI does not execute and a Gate request never runs anything. This ADR has the bridge execute **steering commands** (dispatch, kill, message, permission decisions), but only when a token-authenticated route asks it to. A Gate request line still runs nothing, and **no cell ever starts because a line appeared**: the `dispatch-approve` line is an audit record the bridge writes after it handles `POST /cells`. Final rewording is in the Comments.
- **The 2026-09-28 event-source decision** (transcript tailing as the source, hooks as the fallback) is changed: the child's stdout stream is now the primary source, through the same parser; transcript tailing stays as a secondary feeder if S2 needs it, and the hook design stays only in the optional `--bg` mode. The user's reasons (one reader for animation and cost, no polling) still hold. Needs the user's acknowledgement.
- **ADR 0011 decision 1** says the daemon replaces `apps/bridge`. Amended: the bridge grows in place and no separate daemon exists. Decision 2's "zero Board write paths" is unchanged. ADR 0011's unauthenticated `POST /requests` is tightened to require the token and Origin.
- **ADR 0001** is consistent in letter for headless (CLI only, no SDK, no API key); the intent (plan usage) depends on the unconfirmed billing fact and the user's answer (decision 2, spike S5).
- **ADR 0004** is refined, not changed: the verbs stay; the interface is one `spawn` returning a cell process, `approve` becomes `decide` over an event, and `capabilities` is added (`attach` becomes `handover`, since live pairing is not offered).
- **ADR 0008 decision 8** is fulfilled by this ADR. **ADR 0007**'s `daemonStateSource` is this ADR's `cells[]` plus `cell` events, consumed by `snapshotStateSource`.
- **ADR 0002 and CLAUDE.md** disagree on the limit (one by default, `max_concurrent_cells: 2` now). This ADR reads the constant from `policy.mjs` and cites CLAUDE.md. ADR 0002's usage auto-pause may not see headless consumption (decision 2).

**Consequences.**

- Three implementation tickets follow, in slice order. The orchestrator writes them (`to-tickets`); slice 1 needs the spike results before its qa specify, so the first ticket is the conformance script and S1 to S6, run by someone with the owner's login.
- How the bridge is started, so that it has the owner's login and shows the launch URL, is an open question for the user (decision 7). On this machine `claude` may not be on PATH, so `DEN_CLAUDE_BIN` can point at the desktop app's bundled binary.

When the orchestrator should read the UI-woken prompt as approval, the existing "dispatch-approve acts as if the user answered in chat" step already covers it, with the forgery residual stated in decision 3; slice 3 would need a genome change, which only the orchestrator makes with the user's permission.
